# ADR-0009: 记忆维护闭环——注入可见性 + 规则约束，不做自动写库

> 状态: Accepted
> 日期: 2026-08-13
> 关联: MR-011（知识浏览/纠错闭环，主体仍 OPEN）

## 背景

记忆会静默过期（配置变更、结论推翻、行为规则更新），但召回时没有任何陈旧度信号，
agent 无从判断一条记忆是否还成立；维护完全依赖 agent 自觉（SKILL.md 的 update 指引
存在但无触发条件），2026-08-13 实测出现"同一会话内早前沉淀的记忆 1 小时后已过期、
直到用户追问才被发现"的案例。

## 选项

- A: 仅强化规则（AGENTS.md/SKILL.md 加"结论变更后主动 update"）；
- B: A + 注入可见性：超过 90 天的记忆在注入上下文标注「记录于 N 天前」；
- C: B + 后端定时扫描脚本（LLM 判定陈旧记忆，生成候选清单）；
- D: B + 自动写库（扫描后自动 update/forget，无需人工确认）。

## 决策

选择 **B**：规则约束 + 注入时标注陈旧度。明确**不做**定时扫描脚本（C）与自动写库（D）。

## 理由

- 最痛的失败模式是"陈旧记忆静默存在、agent 无从感知"；B 在每次召回的当下给出信号，
  把维护责任落到"内容被使用的那一刻"，而不是依赖定期巡检；
- 写侧闭环已存在：新记忆与旧记忆矛盾时 relation_service 自动降级旧版 is_latest=FALSE；
  缺的是读侧信号，B 恰好补上；
- 不做 D：LLM 误判会覆盖用户知识，与 ADR-0006"会话摘要不自动入库"的信任原则一致，
  自动写库风险远大于收益；
- 不做 C：旧≠过期（用户偏好可长期成立），纯年龄扫描信噪比低；真正的矛盾信号只在
  内容被使用时才出现。等出现实际需求再上 LLM 辅助巡检不迟；
- MR-011（用户可见的知识浏览/纠错 UI）是更大的独立项目，保持 OPEN，B 是其最小前置。

## 后果

- 正面：agent 在召回时能看到「记录于 N 天前」并主动 search/update；规则层有明确触发
  条件（结论/行为变更后收尾前必须核对相关记忆）；零写库风险、零 LLM 成本；
- 负面：标注只覆盖记忆（不含画像/文档片段）；超过 90 天但仍在有效期内的记忆会持续
  显示标注（token 成本为每条约 10 字符，可忽略）；
- 跟进：MR-011 UI 闭环；若未来要做定时巡检，需新 ADR 并设计人工确认流程。
