# Memory Recall 文档沉淀规范（Docs-as-Records）

> 状态: ACTIVE · 版本: v1.0 · 最后更新: 2026-08-13
>
> 本规范是项目文档管理的总规则，供人类与 AI Agent 共同遵守。
> 简要版见 [AGENTS.md](../AGENTS.md#文档沉淀规范docs-as-records强制)。

## 0. 为什么要有这套规范

项目的每一项工作——功能讨论、方向探讨、调研、决策、设计、问题发现——都是项目资产。
**信息不允许只存在于对话里**：对话会消失，文档不会。所有工作产出都要落成文档，
沉淀在仓库中，可追溯、可检索、可被后续 Agent 与人类复用。

三条铁律：

1. **无文档，不算完成**：任何讨论/调研/决策/设计结束后，必须产出对应文档；
2. **类型分流**：不同类型的产出进不同的目录，谁都能按图索骥；
3. **状态永远明确**：每个文档必须标注状态（当前为真 / 草稿 / 已被取代 / 归档），
   任何人（包括 Agent）拿到文档都能判断"这还能不能信"。

## 1. 目录职责总览

```
docs/
├── README.md               # 文档中心：索引 + 入口
├── DOCUMENTATION_GUIDE.md  # 本规范
├── STATUS.md               # 实时任务状态：活跃工作/下一步/等待项（每次收尾更新）
├── PROJECT_PLAN.md         # 项目/产品长期规划（当前生效）
├── ENTITY_DESIGN.md        # 领域模型与实体设计（当前生效，版本化）
├── ISSUES.md               # 已知问题与改进建议（MR-xxx 编号，追加/更新）
├── DEPLOYMENT.md           # 部署与运维（当前生效）
├── decisions/              # 决策记录 ADR（追加制，不可修改已接受决策）
├── notes/                  # 过程记录：讨论/调研/方向探讨（按日期命名）
├── designs/                # 产品/功能设计（版本化，当前生效唯一）
└── archive/                # 过时/被取代文档的最终归宿（不进入知识库）
```

| 产出类型 | 放哪里 | 生命周期 |
|----------|--------|---------|
| 讨论、调研、方向探讨、头脑风暴 | `docs/notes/` | 永久保留，只追加 |
| 架构/产品/技术决策 | `docs/decisions/` | 追加制，被取代时写新 ADR |
| 产品/功能设计（方案、权衡、版本） | `docs/designs/` | 版本化，当前生效唯一 |
| 已知问题、改进建议 | `docs/ISSUES.md` | 追加，修复后标记已解决 |
| 当前为真的知识（规划/领域模型/部署） | `docs/` 根目录 | 版本化，过时移 archive |
| 实时任务状态（现在该做什么） | `docs/STATUS.md` | 每次收尾更新，历史进 notes |
| 过时内容 | `docs/archive/` | 只读，不修改正文（可补充归档说明） |

## 2. 决策记录（ADR）

**ADR = Architecture Decision Record（架构决策记录）**，一种业界常用的轻量决策文档
（2011 年由 Michael Nygard 提出）：每个有影响的方向性取舍写一篇小文档，记录
背景、选项、决策、理由与后果，按编号永久存档。它不是方案设计（方案见 §5 设计文档），
而是"我们为什么这么选"的答案。

**只有明确作出的取舍才写 ADR**（用户确认或团队达成一致）；包括但不限于：产品定位、
架构选型、数据模型变更、召回策略调整、新功能范围界定、"不做 X"的决定。

**讨论过程不产生 ADR**：候选方案、讨论记录、权衡都写在 notes 里；
讨论收敛、结论明确后，才把结论落成 ADR。ADR 是"决策的结果"，不是"讨论的容器"。

规则：

- 存放位置：`docs/decisions/NNNN-短横线slug.md`，编号从 0001 递增，**不回收编号**；
- 状态机只有两条：`Accepted → Superseded`：
  - **Accepted**：已接受，当前有效；
  - **Superseded**：被后续新 ADR 取代，不再有效，但正文保留作为历史。
    例如 ADR-0001 决定"用 A"，后续 ADR-0005 决定"改用 B"，则 0005 声明 `Supersedes: 0001`，
    0001 同时更新为 `Superseded by: 0005`（双向链接）——后人打开任意一篇都能看到
    "当初为什么选 A、后来为什么改 B"。
- **提案被否决怎么处理**：没有 Rejected 状态，因为否决本身就是一条决策——
  - 值得后人知道"为什么不做"的（影响方向、可能被重新提出）→ 写一条 Accepted 的 ADR，
    决策内容为"不采用 X"，理由里记录否决原因；
  - 随手否决的候选方案 → 留在 notes 即可，不写 ADR。
- **不可变记录**：Accepted 之后不修改决策正文；状态变更（Accepted → Superseded）
  与取代链接是状态机的一部分，**不受"正文冻结"限制**。
- 模板见 [docs/decisions/README.md](decisions/README.md)。

### 2.1 ADR 与实施状态（Accepted ≠ 已实现）

ADR 只表达决策生命周期（Accepted / Superseded），**不表达实施进度**。
"决策已接受但尚未开发"是常态而非异常——决策先于实现，实施可能有排期、有依赖、
甚至长期不做。因此：

- 每个 Accepted ADR 必须在 [docs/STATUS.md](STATUS.md) 的"ADR 实施跟踪"表登记实施状态：
  未开始 / 部分实现 / 已实现，并链接回 ADR（有实施计划/设计文档时一并链接）；
- 新建 ADR 时同步登记；实施状态变化（开工、部分完成、完成）时更新该表，
  不得只存在于对话里；
- 实施完成：标注"已实现"并记录 commit/版本，然后从活跃跟踪表移除
  （历史进 notes，有设计文档的在其上标注实现版本）；
- 被 Superseded 的 ADR：删除或标注其跟踪条目，不再跟踪已失效决策；
- ADR 正文冻结不受影响：实施状态永远不写回 ADR 正文，
  也不给 ADR 状态机增加"实施中/已实现"等档位。

## 3. 过程记录（notes）

**讨论、调研、方向探讨都是过程，都要留痕**。不要求内容成熟，但必须有骨架。

规则：

- **大小分流**：
  - 大型主题（一次实质讨论/调研）→ 独立文件 `docs/notes/YYYY-MM-DD-短slug.md`，
    一天多篇用 `-2`、`-3` 后缀；
  - 细碎信息（随手记录、小观察、一句话结论）→ 当日汇总
    `docs/notes/YYYY-MM-DD-note.md`，每条带小标题；累积到可独立成篇时再拆出；
- 结构固定：背景 → 讨论要点/调研发现 → **结论** → **下一步** → **未决问题**；
- "结论"和"下一步"可以为空，但要显式写"暂无结论"而不是缺节；
- 过程记录一旦写完就不删除；后续有新进展，追加新篇并互相引用，不要改写旧篇；
- 模板见 [docs/notes/README.md](notes/README.md)。

## 4. 设计文档（designs，版本化）

**产品设计必须有版本和"当前生效"的唯一文档**。

规则：

- 一个主题一个子目录（如 `docs/designs/doc-lifecycle/`），目录内：
  - `v1.md`、`v2.md`... 按版本号排列（git 历史是兜底，文件名是主版本线）；
  - `LATEST.md` 是软链式入口，指向当前生效版本（内容为指针 + 摘要）；
- 状态：`草稿 → 生效 → 被取代`；同一主题**只能有一个生效版本**；
- 设计被实现后，保持"生效"并标注实现版本/commit；实现偏离设计时更新设计或写新版本，而不是让文档撒谎；
- 领域级设计（如实体模型）直接放 `docs/` 根（当前生效），变更时更新版本号并记录变更原因；
- 模板见 [docs/designs/README.md](designs/README.md)。

## 5. 一个 Feature 的完整文档流

做任何一个功能（或大改动），文档按阶段沉淀，不遗漏：

| 阶段 | 产出 | 位置 |
|------|------|------|
| 想法/讨论/调研 | 过程记录（背景/要点/结论/下一步/未决） | `docs/notes/YYYY-MM-DD-*.md` |
| 方向取舍：做不做、选哪个方案 | 决策记录 ADR | `docs/decisions/NNNN-*.md` |
| 方案设计：怎么做（含验收标准） | 设计文档 v1（草稿→生效） | `docs/designs/<feature>/v1.md` |
| 实现 | 代码 + 测试；设计文档标注"已实现" | `apps/` + `apps/api/tests/` |
| 测试与验收 | 验收标准在设计文档内；测试用例在测试代码；验收结果回填设计文档 | `docs/designs/<feature>/` |
| 过程中发现的问题 | issue 条目 | `docs/issues/MR-xxx.md` |
| 发布 | CHANGELOG + 设计文档保持生效 | `apps/api/CHANGELOG.md` |

要点：

- **验收标准写进设计文档**：每个设计 v1 必须含"验收标准"节；
- **测试用例就是代码**（tests/），不需要单独的测试文档目录，避免两份内容互相漂移；
- 小改动（修复 bug）不需要走完整流程：直接 `docs/issues/MR-xxx.md` + 代码即可，
  涉及方向取舍才需要 ADR；
- 一个功能完成后，设计文档保持"生效"并标注实现版本，成为该功能的 spec。

## 6. 问题清单（ISSUES.md 索引 + docs/issues/ 详情）

- 索引：`docs/ISSUES.md`（根目录，进知识库）只放 open 问题表格（ID/标题/严重度/链接），
  一眼看到当前有哪些坑；
- 详情：每个问题一个文件 `docs/issues/MR-xxx-短slug.md`（严重度、证据、建议），
  避免单文档无限膨胀；
- 新增问题：写详情文件 + 更新索引；
- 修复问题：详情文件标记 `已解决` 并记录 commit / 版本，索引移入"已解决"表，
  **不删除文件**（保留问题史）；
- 很老且不再需要的问题可移 `docs/archive/issues/`。

## 7. 文档头部（所有文档必须）

```markdown
> 状态: ACTIVE | ARCHIVED | PROPOSED | ACCEPTED | SUPERSEDED
> 版本: v1.0
> 最后更新: YYYY-MM-DD
> 关联: ADR-0001, MR-010（可选）
```

状态含义：

| 状态 | 含义 |
|------|------|
| ACTIVE / ACCEPTED | 当前为真，可据此行动（ADR 的 Accepted 见 §2，无 Proposed 阶段） |
| PROPOSED / 草稿 | 讨论中，不可作为实施依据（仅用于设计文档等；ADR 不使用） |
| SUPERSEDED | 已被新文档取代，仅历史参考 |
| ARCHIVED | 过时，移入 `docs/archive/` |

## 8. Agent 工作流（强制）

所有后续 Agent（以及人工协作）遵守以下 checklist：

**任务开始前**：

1. 读 [docs/README.md](README.md) 索引，定位相关生效文档；
2. 读 [docs/ISSUES.md](ISSUES.md) 确认是否已有相关 issue；
3. 相关领域先读 [docs/ENTITY_DESIGN.md](ENTITY_DESIGN.md) 与 `docs/decisions/`。

**任务进行中**：

4. 新讨论/调研/方向 → 写 `docs/notes/`；
5. 方向性取舍已明确 → 写 `docs/decisions/`（Accepted；讨论过程在 notes）；
6. 新设计或设计变更 → `docs/designs/`（版本化）或更新根目录生效设计；
7. 发现新问题 → 写 `docs/issues/MR-xxx.md` + 更新 [docs/ISSUES.md](ISSUES.md) 索引。

**任务结束前**：

8. 检查本次工作是否产生上述任意一类信息，未落文档不算完成；
9. 更新 [docs/STATUS.md](STATUS.md)（活跃任务/下一步/等待项；收尾必做，防止"下一步只存在于对话里"）；
10. commit 时文档变更与代码变更一起提交（`docs:` 前缀）；
11. 更新 [docs/README.md](README.md) 索引中受影响的行。

## 9. 与知识库的关系（重要）

- opencode 插件默认导入 `docs/*.md`（仅根目录一层）作为项目知识；
- 因此 **docs/ 根目录 = 系统也会读的当前事实**；`decisions/`、`notes/`、`designs/`、
  `archive/` 子目录默认不进注入上下文（需要时通过搜索 API 获取）；
- 这个边界是特性不是缺陷：过程与历史不污染每次注入，当前事实常驻知识库；
- 若某主题需要常驻知识库，把它写成根目录 ACTIVE 文档，而不是靠调插件。

## 10. 常见问题

**Q: 讨论完忘了写笔记怎么办？**
A: 补写。日期写实际发生的日期，标题注明"补记"；有记录好过没记录。

**Q: 一个决策改动很小，也要写 ADR 吗？**
A: 影响代码行为、产品方向、数据模型、对外契约的都要；纯实现细节不用。

**Q: 设计文档和 ADR 的区别？**
A: ADR 回答"我们为什么这么选"（决策与理由）；设计文档回答"我们打算怎么做"（方案与版本）。

**Q: ADR 已接受但还没开发，怎么表达？**
A: 决策与实施是两件事：ADR 保持 Accepted 即可，正文不动；实施状态登记在
   STATUS.md 的"ADR 实施跟踪"表（见 §2.1），完成后在设计文档上标注"已实现" + commit 收尾。

**Q: 旧文档太多，清理原则？**
A: 移 `docs/archive/`（git mv），在 archive README 补一行原因；不要直接删文件，历史也是资产。
