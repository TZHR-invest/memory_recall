# Recall Trace - 召回链路可观测性设计

> **文档说明**：本文档描述 Recall Trace 功能的背景动机、功能设计与预期效果。实现细节将在设计确认后另行补充。
>
> **状态**：设计讨论稿
>
> **相关代码**：`src/services/core/context_inject_service.py`（多路召回管线）、`src/services/core/memory_store.py`（搜索与图谱遍历）、`src/services/core/semantic_dedup_service.py`（去重）

---

## 1. 为什么做（背景与动机）

### 1.1 现状：召回是一个黑盒

系统的召回核心是 `context-inject` 的多路管线：画像注入 → 向量检索 → 记忆图谱扩展 → 实体图谱扩展 → 文档 chunk 检索 → 语义去重 → 格式化输出。

但对外只暴露了**合并后**的结果：`sources`（每条候选的 id + content）和 `stats`（总数 / 去重数）。一次召回实际发生了什么，外部完全不可见：

| 环节 | 现状不可见的信息 |
|------|-----------------|
| 向量检索 | 召回了哪些记忆、各自相似度多少、**被阈值过滤掉了什么** |
| 记忆图谱扩展 | 从哪个节点出发、沿 updates/extends/derives 走到哪、扩展出的记忆是否进了最终结果 |
| 实体图谱扩展 | 从哪个实体出发、路径怎么走、找到的关联记忆是什么 |
| 文档 chunk 检索 | 命中哪些 chunk、相似度多少 |
| 语义去重 | 哪些候选被判重丢弃（**被丢弃的可能恰好是有价值的信息**） |
| 参数影响 | threshold / graph_depth / dedup_threshold 等配置改动后的实际效果 |

### 1.2 痛点

1. **调参靠猜**：`context-inject` 有大量可调参数（相似度阈值、图谱深度/节点数、去重阈值、各开关），但没有逐路数据就无法判断"结果变差是因为向量没召回，还是图谱没走通，还是被去重误杀"。
2. **无法解释死因**：用户说"这次注入缺了某条记忆"，当前系统无法回答"它是在哪个环节被过滤掉的"。找不到原因就无法修复。
3. **决策缺数据**：类似"2026-04-24 移除最近记忆补位"（`context_inject_service.py` 中的注释）这类质量决策，此前只能靠经验观察，没有数据佐证；未来再做类似决策时，需要 trace 数据作为依据。
4. **回归无抓手**：代码改动后召回质量是否退化，没有历史数据可对比。

### 1.3 目标

把召回链路从"黑盒"变成"可观察、可解释、可对比"，为召回质量调优提供数据基础。

## 2. 要怎么做（功能设计）

### 2.1 总体思路：两层设计

```
┌─────────────────────────────────────────────┐
│  第一层：Trace 数据层（核心）                 │
│  在召回管线各环节埋点，一次召回 = 一条 Trace  │
│  记录每条候选的来路、相似度、去留、耗时       │
└─────────────────────────────────────────────┘
                     │ 只读读取
┌─────────────────────▼───────────────────────┐
│  第二层：展示层（Debug 页面）                 │
│  搜索框（真实触发召回并记录）                 │
│  最近 Trace 列表 + Trace 详情逐路展开         │
│  对比模式：同 query 不同参数并排              │
└─────────────────────────────────────────────┘
```

### 2.2 Trace 数据模型（一次召回一条记录）

```
recall_trace
├─ request_id        # 一次召回唯一 ID
├─ timestamp         # 发生时间
├─ container_tag     # 容器（数据归属）
├─ query             # 查询文本（原始 + 向量化后长度）
├─ config            # 本次召回使用的完整配置快照（用于复现）
├─ channels          # 逐渠道明细（核心）
│   ├─ vector        # 向量检索：全部候选 [{id, content, similarity, passed}]
│   │                #   passed=false 即被阈值过滤，记录阈值
│   ├─ memory_graph  # 记忆图谱：扩展路径 [{from_id, relation_type, to_id}] + 新加入候选
│   ├─ entity_graph  # 实体图谱：路径 [{entity_name, relation_type}] + 找到的记忆
│   ├─ chunks        # 文档检索：候选 [{chunk_id, document_id, similarity, passed}]
│   └─ profile       # 画像：注入的 static/dynamic 条数
├─ dedup             # 去重明细：{kept: [...], dropped: [{id, dropped_by(与谁重复), similarity}]}
├─ final_output      # 最终输出：实际注入的条目顺序（与线上一致）
├─ elapsed_ms        # 总耗时 + 各渠道耗时
└─ meta              # 版本号（代码版本，便于对照）
```

**设计要点**：
- **必须记录被过滤/被丢弃的候选**，而不只是幸存者——否则只能证明"活着的"，不能解释"死因"。
- **config 全量快照**进 trace：同一 query 在不同参数下的结果差异可以对照。
- 候选内容只存截断文本（如前 200 字符），控制存储体积；全量内容可关联记忆 ID 查询。

### 2.3 埋点位置（不改变召回逻辑，只记录）

| 环节 | 埋点位置 | 记录内容 |
|------|---------|---------|
| 向量检索 | `_get_memories` 中 `memory_store.search` 调用处 | 全部返回 + 阈值 |
| 记忆图谱扩展 | 遍历 relations 处 | 扩展路径、加入的节点 |
| 实体图谱扩展 | 实体遍历 + `find_memories_by_entities` 处 | 实体路径、找到的记忆 |
| 文档检索 | `_get_chunks` 中 `search_chunks` 调用处 | 全部返回 + 阈值 |
| 画像 | `_get_profile` 处 | 注入条数 |
| 去重 | `semantic_dedup_service.deduplicate` 调用处 | 保留/丢弃对 |
| 计时 | 各环节包裹 | 每渠道耗时 |

### 2.4 存储与开关

- 落库 `recall_traces` 表：主字段 + `channels`/`dedup` 用 JSONB。
- **TRACE_ENABLED 开关**：默认开启（调试期），生产可关；关闭时零开销。
- **采样率**：高并发时可只记录 N% 或按 query 哈希采样。
- **保留期**：如 7 天，超期清理（带查询的调试记录可标记保留更久）。
- 写入异步化：trace 写入不阻塞召回响应。

### 2.5 Debug 页面（展示层）

页面三个功能区：

1. **搜索区**：输入 query + 可调 config（阈值、图谱开关、去重阈值），点击后真实触发 `context-inject`，即时生成一条 trace 并展示详情——**所见即所查，且与线上同一管线**。
2. **Trace 列表区**：按时间倒序展示最近 trace（query、耗时、命中总数、各渠道条数摘要、config 指纹），点击进入详情。
3. **Trace 详情区**：逐渠道展开，每个渠道一个区块：
   - 向量路：候选列表带相似度色阶，被阈值过滤的置灰并标注"低于阈值 0.60"
   - 图谱路：渲染扩展路径（节点 + 关系类型），标注"经此扩展加入"的记忆
   - 去重路：kept/dropped 分组，dropped 标注"与 #xxx 重复 (0.87)"
   - 底部：最终输出顺序 + 各渠道耗时条形图

4. **对比模式**（进阶）：同一 query、两套 config 并排渲染两条 trace，差异高亮——用于参数调优。这是调参效率的核心工具。

### 2.6 只读 Trace API

- `GET /debug/traces`：分页列表
- `GET /debug/traces/{request_id}`：单条详情
- `POST /debug/traces/search`：触发一次真实召回并返回 trace（需 write 权限的 debug key）
- 与现有认证体系一致，仅对 debug 权限的 API Key 开放

## 3. 做成什么样的效果（预期效果）

### 3.1 一次 Trace 的典型形态（示意）

```
┌──────────────────────────────────────────────────────────────┐
│ Trace #20260809-001  |  query: "张三在哪里工作"              │
│ 耗时 48ms | 候选 12 → 注入 6 | config: v2 (threshold=0.5)    │
├──────────────────────────────────────────────────────────────┤
│ [向量] 阈值 0.50                                             │
│   ✓ 0.82  "张三在字节跳动做算法工程师"                       │
│   ✓ 0.61  "张三和张四一起做了大模型项目"                     │
│   ✗ 0.44  "张四喜欢喝咖啡"        ← 低于阈值，未进入        │
│                                                              │
│ [记忆图谱] updates/extends 扩展                               │
│   mem_a --extends--> mem_b ("张三跳槽去了 Supermemory")  ✓加入│
│                                                              │
│ [实体图谱] 张三 -works_at-> 字节跳动 → 找到 2 条记忆          │
│   ✓ "字节跳动的团建活动"                                     │
│   ✓ "张三在字节的工位是 3 层"                                │
│                                                              │
│ [文档 chunk]                                                 │
│   ✓ 0.73  README.md#chunk-12  "...张三的交接文档..."          │
│                                                              │
│ [去重] 丢弃 1 条                                             │
│   ✗ "张三目前就职于字节" → 与 "张三在字节跳动做算法工程师"   │
│     重复度 0.89，丢弃                                        │
│                                                              │
│ [最终注入顺序] 6 条（含来源标注）                              │
└──────────────────────────────────────────────────────────────┘
```

这个例子直观回答了三个之前无法回答的问题：
- "为什么没有召回到张三跳槽的信息？" → 记忆图谱扩展走了 extends，加进来了
- "为什么某条记忆没出现？" → 去重丢弃了，且能看到和谁重复
- "调 threshold 有没有用？" → 对比模式直接看出 0.44 那条被过滤

### 3.2 使用场景

| 场景 | 用法 |
|------|------|
| 调参 | 对比模式：同 query 不同 config 并排看差异 |
| 定位缺失 | 详情页看某条记忆死在哪个环节（阈值/去重/图谱没走通） |
| 回归测试 | 定期跑固定 query 集，比对 trace 摘要是否退化 |
| 图谱质量审计 | 看实体图谱扩展路径，判断 LLM 抽取的关系是否合理 |
| 数据驱动决策 | 类似"移除最近记忆补位"的决策，现在有数据支撑 |

### 3.3 边界与取舍

- 不追求成为通用可观测性平台，只服务召回链路这一个场景。
- 不做实时流式展示；列表 + 详情即可，数据是调试定位用途，秒级延迟可接受。
- Trace 数据是敏感数据（含用户记忆内容），页面与 API 必须沿用现有认证与容器隔离；生产环境默认仅 debug key 可见。
- 页面定位为**内部调试工具**，不产品化，放在现有 `web/` 静态页体系内。
