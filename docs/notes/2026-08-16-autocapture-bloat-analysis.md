# 自动捕获膨胀分析（2026-08-16）

> 状态: 草稿 · 2026-08-16（v2：方案经 review 完善，见 §3 修订说明）
> 触发：用户观察 2026-08-15 自动捕获大量写入记忆（518 条），询问是否正常；本文档为数据驱动的深入分析与优化方案。
> 数据源：memory_recall 库（pgvector）+ 插件/后端代码核对。时区均为 Asia/Shanghai。

## 1. 结论先行

**机制正常，量级失控，需要优化。** 自动捕获按设计每轮 turn/end 触发、LLM 蒸馏后落库，但当前实现缺少
节流、写入侧语义去重形同虚设、无生命周期管理，导致重活日单日写入 518 条（平日 8~31 条），
其中绝大多数（~98%）后续从未被注入使用。注入侧三层去重（会话内摘要 / per-agent LRU / exclude_memory_ids）
运转正常，问题全部出在**写入侧**。

## 2. 数据事实

### 2.1 写入量

| 日期 | 写入条数 | 备注 |
|------|---------|------|
| 07-18 ~ 08-13 | 8~31/天（中位数 ~12） | 基线 |
| 08-14 | 198 | 开始上量（dsh-lan-access 排障夜） |
| **08-15** | **518** | 尖峰，占全库有效记忆（2374）的 22% |
| 08-16（截至傍晚） | 90 | 仍在高位 |

- 时间分布：**00:00~04:00 写入 252 条（占 49%）**；03:00 单小时 103 条（≈每 2 分钟一批）。
- 容器分布：project-dsh-plugins 311、project-memory_recall 195、hermes 8、用户容器 4。
- 类型分布：learned-pattern 400（77%）、constraint 63、preference 34、error-solution 10、其余 11。

### 2.2 批次 vs 设计

- 设计（重构后记录）：每 5~10 分钟一批、每批 ≤5 条；prompt 硬性"最多 5 条，宁缺毋滥"。
- 实测（按分钟聚类 179 个活跃分钟）：169 批 ≤5 条，**10 批超 5 条（6~10 条）**，最大一批 10 条。
- 根因（代码核对）：capture.js 写库时 `extracted.memories.slice(0, 10)` —— **上限是 10 不是 5**，
  prompt 的"最多 5 条"没有被插件硬性执行。
- 无批节流：capture.js 每轮 turn/end 直接调 /extract-memory，无 debounce；设计中的"5~10 分钟一批"
  只是对话节奏的观测结果，不是实现。高频轮次（凌晨排障、多会话并发）时写入速率随轮次线性放大。

### 2.3 冗余

| 指标 | 数值 |
|------|------|
| 同日近似对（embedding ≥0.85） | 21 对（≥0.80 共 52 对） |
| 跨日冗余（08-15 vs 更早存量 ≥0.85） | 仅 2 条 |
| 写入侧合并命中（merged_count>0） | 1/518（阈值 0.95 下几乎不触发） |
| 精确重复 | 1 组 2 条 |

- 冗余形态是**同日主题碎片化**：同一任务的连续多轮各自蒸馏，产出多条近似变体
  （如 Tailscale 地址 2 条、"install.sh --restart 激活"3 条、端口 3080 多主题重复），
  而非跨日重复 —— 说明蒸馏缺少**跨轮聚合/跨批去重**。
- 后端写入侧有语义查重（memory_store._check_similar_memory），但阈值
  `MEMORY_MERGE_THRESHOLD=0.95`（config.py:84）≈只拦完全重复；且 merge 只计数
  （merged_count+1）不吸收内容，即使命中冗余也仍在库里。

### 2.4 价值密度（08-15 写入的记忆）

| 指标 | 数值 |
|------|------|
| 08-15 17:00 之后被注入命中 | 10/518 ≈ **2%**（同期注入命中 70 条中 60 条来自更老记忆） |
| 后续被版本化修正 | 29/518（5.6%） |
| is_static 占比 | 242/518（47%）——其中 learned-pattern 178 + constraint 38 被标 static（设计上仅 preference 应 static） |

- 凌晨批次的样本内容多为**一次性任务细节**（端口/地址/临时命令/重启流程），问题解决后即失去跨会话价值，
  与蒸馏 prompt 的排除标准（流水账/系统描述/无验证泛论）不重叠 —— 说明排除标准还缺"一次性任务细节"类。
- static 纪律问题：242 条 static 中 216 条非 preference。画像缓存（用户容器 27 static）暂未显著受污染，
  但项目容器 static 记忆持续堆积会侵蚀静态注入质量与画像语义。

### 2.5 成本

| 项 | 08-15 | 平时 |
|----|-------|------|
| embedding 调用（memory 类） | 717 次 | 23~57 次/天 |
| embedding 调用（context 类） | 630 次 | 96~125 次/天 |
| 蒸馏 LLM 调用 | 数百次（每轮 1 次） | — |
| 有效记忆总量 | 2374（08-15 一天占 22%） | — |

- 库无自动清理：forget_after 字段存在但**无任何定时任务消费**（已核对，只有 API key 过期机制）；
  旧版本 1291 行（设计产物）、forgotten 84 条。库只增不减。
- 存储本身不是瓶颈：2374 条 × ~50 字 ≈ 12 万 token，pgvector 本地存储几乎免费；
  真实成本是 embedding/LLM 外部调用与注入质量稀释。

### 2.6 机制核对汇总（代码事实）

| 项 | 现状 | 问题 |
|----|------|------|
| capture.js 批上限 | slice(0, 10) | 与 prompt"最多 5 条"不一致 |
| capture.js 节流 | 无（每轮触发） | 高频轮次写入失控 |
| 写入侧去重阈值 | 0.95（config.py:84） | 近似重复全漏 |
| 跨轮聚合 | 无 | 同主题碎片化 |
| 蒸馏排除标准 | 流水账/系统描述/泛论 | 缺"一次性任务细节" |
| 生命周期 | 无自动遗忘 | 库只增不减 |
| 注入侧三层去重 | 正常 | —（本分析未触及） |

## 3. 优化方案 v2（review 完善版）

### 3.1 对 v1 方案的 review 结论（为什么修订）

1. **覆盖范围不足**：v1 主要改 dsh 插件侧，但**opencode 插件同样调 /extract-memory 写库**
   （compaction 捕获，client.ts:373），hermes/deepseek-tui 亦同。插件侧修改只覆盖 dsh 一个来源；
   **节流/去重/配额应下沉到后端端点（/extract-memory 与 POST /memories），一处修改所有插件受益**。
2. **成本分析缺位**：v1 未论证去重成本。落库前语义去重需要候选条目的 embedding——但这些条目
   落库后本来就要异步算 embedding（asyncProcess=true），**去重把 embedding 提前且丢弃的条目不再落库**，
   净成本不增反减；保留条目存在重复计算，可后续复用（见 3.2-6）。
3. **第四批过重**：存储非瓶颈（§2.5），自动遗忘误删风险高、且 ADR-0014（置信度两轴）未落地前
   "未命中即衰减"的信号不可靠 —— **降级为 P3 可选项**，重点转为"防新增"而非"清存量"。
4. **遗漏零风险减量手段**：captureMinLength 目前 40 字符，凌晨短轮（每轮蒸馏 1~2 条）说明门槛偏低；
   提高到 100 字符可零风险减量，v1 未覆盖。
5. **信息不丢的保障未写明**：会话对话本身完整保留在 dsh session 事件流（session.jsonl），
   捕获丢弃/节流跳过只是"不入长期记忆库"，不是"信息丢失" —— 这一点消除了"节流会丢信息"的顾虑。
6. **实施安全网缺失**：v1 未写明配置开关可回退、测试先行、dsh bundle 重建 + 终端重启的防崩纪律。

### 3.2 v2 方案（四批）

**第一批：写入门槛与节流（零/低风险，先做）**

1. **硬性上限对齐**：capture.js 写库处 `slice(0, 10)` → `slice(0, 5)`，与蒸馏 prompt 一致
   （apps/api/src/plugins/dsh/capture.js，bundle 需重建）。
2. **提高捕获门槛**：captureMinLength 默认 40 → 100 字符（config.js），短轮（寒暄/快速问答）不再触发蒸馏。
3. **会话级节流**：capture.js 增加会话级 lastCaptureAt，两次蒸馏间隔 < captureMinIntervalMs
   （新增配置，默认 600000ms=10 分钟）时跳过本轮，摘要随下轮累计（滑动窗口，上限 captureMaxChars）。
   信息不丢：对话本就在 session 事件流。

预计效果：峰值日 518 → ~80~120；>5 条/批归零；embedding 调用随之下降。

**第二批：去重下沉到后端（核心收益，所有插件受益）**

4. **/extract-memory 内嵌去重**（apps/api/src/api/memories.py，extract_memory_from_summary）：
   - 蒸馏结果非空时，对每条候选用 embedding 检索同容器 top-1 相似记忆（pgvector，本地毫秒级）；
   - 相似度 ≥ 0.85（可配 CAPTURE_DEDUP_THRESHOLD）丢弃，响应中返回 dropped 列表（content+reason）供插件审计；
   - 检索到的相似记忆 content 同时作为 prompt 上下文（"已保存的相似记忆，勿重复提取"）——
     这同时实现跨批去重（v1 第三批第 8 条并入此处，检索天然覆盖容器全量而非仅本会话）。
   - 所有插件（dsh/opencode/hermes/deepseek-tui）自动受益，无需逐个改插件。
5. **异步写入兜底**（memory_store.py / memories.py）：POST /memories 支持 metadata._capture=true 标记
   （插件 addMemory 传入）；process_embedding_async 的相似检查按来源选阈值：捕获 0.85 / 显式 0.95（现状），
   命中即 DELETE 新行并记日志。防多会话并发竞态（写时互相不可见的窗口由兜底覆盖）。
6. **（后续优化，非本期）** extract-memory 返回候选 embedding，插件落库时传给 POST /memories 复用，
   消除保留条目的二次 embedding 计算。

预计效果：同日近似对（≥0.85）基本归零；碎片化变体在蒸馏环节被拦下，不再进库。

**第三批：蒸馏质量（prompt 迭代，第二批落地后观测再调）**

7. **排除"一次性任务细节"**：/extract-memory prompt 增加硬性排除第 5 类，边界明确定义，防过度排除：
   - 排除：排障过程步骤、临时地址/端口、一次性验证命令（任务完成后失效）；
   - 保留：长期有效的连接信息/配置/规则（如"服务地址 X 是长期入口"）。
8. 观测 3~5 天：写入量、dropped 量、learned-pattern 占比、注入命中率对比。

**第四批：存量治理（一次性 + 长期可选项）**

9. **static 纪律审计（一次性，可回滚）**：脚本列出非 preference 的 static 记忆（当前 216 条）及其
   注入/画像命中情况 → 用户确认清单 → 降级 dynamic（记录原值可回滚）。
10. **写入路径约束**：统一规则"仅 preference 可 static"——memory_store 工具、capture.js（已符合）、
    opencode 插件逐一核对补齐。
11. **自动遗忘（P3，挂 ADR-0014）**：未命中 + 超龄衰减留给置信度两轴落地时一并设计；
    本期不做，避免误删风险与过早复杂度。
12. **写入告警（可选）**：单日捕获写入 >100 条时 stats/overview 提示，防复发。

### 3.3 实施顺序与安全网

1. 顺序：第一批（插件侧，独立可回退）→ 第二批（后端，一处修改全端受益）→ 观测 → 第三批 → 第四批。
2. 配置可回退：节流开关/间隔、去重阈值、门槛、配额全部走插件 config 与后端 settings，默认值按上文，
   出问题关闭即恢复原行为。
3. 测试先行：dsh 插件 harness.test.js 已有 capture 测试（3 个），新增节流/上限测试；
   后端新增 extract 去重单测（命中/未命中/dropped 返回）；全量 pytest 回归。
4. dsh 插件防崩纪律：改动后 bun build 重建 bundle + node --check + harness 冒烟，
   重启由用户在终端执行 install.sh --restart（agent 绝不自杀式重启宿主）。
5. 后端：docker compose restart api（或确认后执行），health + /extract-memory 实测。

## 4. 历史数据处置建议（待用户拍板）

- 08-15 的 518 条**不物理删除**：其中 29 条被后续修正、10 条被注入过，删除不可逆且收益不确定。
- 建议执行：216 条非 preference static → 降级 dynamic（先出清单确认，可回滚）。
- 可选：凌晨"一次性任务细节"类记忆批量 forget（软删除可恢复）——建议等第三批 prompt 生效后
  对比存量再做，避免现在删了以后又写入新的同类碎片。

## 6. 不做清单（防过度设计）

- 不做自动遗忘/价值衰减（挂 ADR-0014，本期风险大于收益）；
- 不做跨轮摘要的 LLM 聚合重构（复杂度高，节流+去重已覆盖碎片化主因）；
- 不改注入侧（已达标）；不做提取结果本地二次 LLM 校验（成本翻倍，收益未证实）。
