# 召回通道消融 + B 变体定向消融（决定"捕获要不要跑 LLM 提取"）

> 状态: DONE · 日期: 2026-09-22 · 目的: 把"B 会损失多少召回"从推测变成实测，并校正此前引用的错误口径

## 背景：要决定的 B 是什么

B = 让**会话自动捕获**写入的记忆不再跑 LLM 实体/关系提取（捕获占近 7 天写入的 **85%**，1216 条），
以求省下每周最多 ~1200 次实体提取 + ~1200 次关系判定的 LLM 调用。变体：
**B1** 只关捕获的关系判定（保留实体提取）／**B2** 捕获改走快档模型／**B3** 蒸馏顺带产出实体／**B4** 离线批量补提取。

## 方法论（关键：不能拿生产库做实验）

用**隔离副本库 + 第二个 API 实例**，让实验产生的 `recall_traces` / `recall_embedding_logs` 全部落在副本里：

1. `createdb memory_recall_ab` + `pg_dump | psql`（313 MB，秒级）；
2. `docker exec -d -e DATABASE_NAME=memory_recall_ab ... uvicorn main:app --port 8010`
   （**实测 pydantic-settings 中环境变量优先于 `.env`** ⇒ 这样就能完全隔离）；
3. 宿主经容器 IP（`172.19.0.4:8010`）发请求；
4. 样本：`recall_traces` 近 7 天随机 40 条真实 query（带原始 `user_tag`/`project_tag`/`config`）；
   **各变体一律剥掉 `exclude_memory_ids`**（插件的跨轮去重名单，留着会把上次结果排除掉，扭曲对比）；
5. 通道消融＝只改 `config.enable_entity_graph` / `enable_memory_graph`；定向消融＝改副本库数据（见下）；
6. 收尾：停实例 → `dropdb` → 删临时文件。**生产库核对：traces/embedding 日志 10 分钟内 0 新增**（全落在副本）。

**⚠️ API 限流 100 req/60s（`auth.py` 硬编码，进程内计数）**：首轮 160 次调用有 65 次 429，
必须节流（0.65s/次）+ 429 退避重试，否则结果里混入残缺样本。

## 实验一：通道消融（同快照，40 query，基线注入记忆 240 条）

| 配置 | 注入总数 | 消失 | 补位 | 受影响的 query |
|---|---|---|---|---|
| V0 全开 | 240 | 0 | 0 | 0 |
| V1 关实体图 | **240** | 80（33%） | 80 | **37/40** |
| V2 关记忆图 | 232 | 45（19%） | 37 | 21/40 |
| V3 两图全关 | 202（-16%） | 102（42%） | 64 | 40/40 |

**读法**：关掉实体图后**总量不变**——被顶掉的位置被其它候选**完全补位**。也就是说图通道的作用不是
"扩大召回到的东西"，而是**决定召回哪一批**：33% 的注入项被换人，93% 的 query 受到影响。

## 实验二：B / B1 定向消融（改副本库数据，同一批 40 query 重放）

- **B 世界**：删捕获来源的全部图谱数据 —— `memory_entities` 7,219 行 + `memory_relations` 6,383 行 +
  `entity_relations` 3,701 行（后者有 `source_memory_id` 可追溯来源）+ 4,333 个只由捕获支撑的孤儿实体。
- **B1 世界**：只删捕获来源的 `memory_relations`（6,383 行），实体链接与实体关系全保留。

| 世界 | 注入总数 | 消失（次） | 占比 | 唯一消失 id | 其中非捕获 |
|---|---|---|---|---|---|
| 基线 | 240 | — | — | — | — |
| **B1** | 240 | 28 | **11.7%** | 19 | **8** |
| **B** | 240 | 45 | **18.8%** | 32 | **5** |

两世界的注入总量都**不变**（完全补位）⇒ 代价是**换内容**，不是"变少"。

**消失项内容抽样（B 世界，25 条）——是实质内容，不是噪音**：
「代理（8001/8002）不能搬进 QMT 客户端进程内」「跨模块通信的三项硬性契约」「交易通道 Redis 上禁止
volatile-lru 淘汰策略」「LLM 生成的止损价不得高于标的现价 95%」「WSL 与 Windows 的 OpenSSH
authorized_keys 路径不同」「sell_check.log 因 gunicorn 双 worker 写同一 RotatingFileHandler 致轮转异常」…
多为 **constraint / learned-pattern 类硬规则**，正是运维场景最不能漏的一类。

**两个反直觉点**：
1. **B1 不是"近乎无损"**——它换掉 11.7% 的注入项，且 19 个唯一消失项里 **8 个是非捕获记忆**
   （经由"捕获产出的边"才被捞到的间接损失）。此前按历史 trace 估算的"上界 6%"是**低估**。
2. 补位项同样是真记忆（project-config / architecture / error-solution，平均长度更长），
   所以问题不是"召回变少或变脏"，而是"**换了另一批，谁更贴题需要相关性评估才能判定**"——
   但已足以说明这个便宜不能白拿。

## 结论

1. **不做 B，也不做 B1**：代价方向一致（换掉 12%~19% 的注入内容，含高价值约束类记忆），
   而收益只是"省 LLM 调用"——这个收益有不动覆盖的拿法。
2. **改走"降调用次数、不降覆盖"**：**B3**（一次蒸馏调用顺带产出 ≤5 条记忆的实体）或 **B4**（批量提取），
   把"每条记忆一次调用"变成"一窗一次调用"，实体/关系覆盖保持不变。
3. 若仍要压成本，**B2（捕获改快档模型 `deepseek-v4-flash-fast`，实测 0.9–4.8s vs 8.1s）** 是次选，
   但需先评估实体召回变少的质量影响（同一文本 3 vs 7 个实体，技术实体全漏）。

## 顺带校正一个我此前引错的口径（勿再复用）

`recall_traces.summary.entity_graph` 的实现是 **`len(memories) + len(entity_paths)`**
（`recall_trace_service.py:253`）——**把"实体关系遍历步数"也算进去了**，所以"平均每次 22.8 个候选、
是召回主力"的说法是错的。按通道明细（`channels.*.memories` / `.hits`，注意 entity_graph 存的是
`memories` 而不是 `hits`）重算：**vector 7.6 条 / entity_graph 3.7 条 / memory_graph 3.8 条（每次召回）**。
历史 trace 口径下"仅图谱交付"的注入项占 26%（694/2677）——结论方向不变，但数字要用这一版。
