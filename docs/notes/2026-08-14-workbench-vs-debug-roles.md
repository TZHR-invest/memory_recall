# 2026-08-14: 个人工作台 vs debug 页权限切分

> 类型: 讨论 · 日期: 2026-08-14
> 关联: MR-011（知识浏览/纠错）· [memory-confidence](2026-08-14-memory-confidence.md) · ADR-0009（记忆维护闭环）
> 重定位: 已并入 [命题晋升总纲](2026-08-14-proposition-promotion.md)（S3 裁决），讨论改走总纲主线

## 背景

用户想做"个人工作台"——看到并纠正系统记住了什么。现有 debug 页定位是数据洞察。
用户设想：debug 页应为系统管理员角色权限，个人工作台用个人 key。本文记录讨论要点。

## 讨论要点

- **权限切分干净**：debug/observability（trace / embedding 日志 / 召回链路）归系统管理员；
  个人工作台（个人 key，只看自己的 container，确认 / 纠错 / 遗忘）归个人。
  现有 auth（admin key vs 普通 key + `verify_container_ownership` 前缀隔离）天然支持，近零成本；
- **工作台是"写路径"，不只是"看"**：确认/编辑/遗忘/纠错 = confidence 调制的 UI 落点；
- **三者一体**：confidence（数据模型）+ 工作台（交互面）+ 确认/纠错（动作）= MR-011 一件事的三个面；
- **多宿主**：opencode/deepseek-tui/hermes 用户不一定开 web → 核心写能力走 API，让插件也能调，
  工作台只是"可选管理层"，别把纠错能力焊死在 web 里；
- **分两档**：先"只读洞察 + 纠错/遗忘"最小闭环，确认队列（写前把关）下一档再上。

## 结论

暂无结论。方向一致，待定实施顺序与 API 形态。

## 下一步

1. 并入 MR-011（知识浏览/纠错闭环）一起规划；
2. 定义工作台最小闭环的 API 与权限边界（admin vs 个人 key）；
3. 与 confidence 落地绑定（工作台是 confidence 可见/可纠的必要条件）。

## 未决问题

- 工作台是独立 web 页，还是扩展现有 debug 页（角色分流）；
- 纠错动作（确认/编辑/遗忘/反例）的 API 契约；
- 确认队列（写前把关）与事后纠错的优先级与顺序。
