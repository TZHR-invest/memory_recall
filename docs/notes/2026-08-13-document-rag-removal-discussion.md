# 2026-08-13 文档 RAG 子系统去留讨论

> 类型: 方向探讨 → 决策已定（[ADR-0010](../decisions/0010-remove-document-rag.md)）· 日期: 2026-08-13

## 背景

用户提出上层设计疑问：文档管理与记忆管理是否应解耦为两个模块，甚至把文档系统
直接移出项目。本文记录讨论要点与结论。

## 讨论要点

- 现状盘点：文档子系统是完整 RAG 管线（documents/chunks/chunk_entities 表、
  chunking 包 10 文件、/documents* 路由、chunks 召回通道、三插件 document tools），
  与记忆系统并列运行，从不蒸馏为 memories；
- 耦合点集中在召回边界（context-inject 第四条通道、hybrid、去重/cap/trace 的
  chunk 分支），存储层本就分离（memory_store 不感知文档）；
- 角色三分：① 记忆来源（蒸馏入站）② 并行检索语料（RAG）③ 独立文档管理产品；
  现状是 ②+③；
- 场景判断：coding agent 自带文件系统，chunk RAG 与之重叠，是替代品而非缺口；
  文档对记忆的价值在"蒸馏"而非"并列"；
- 召回价值证据：chunks 通道优先级最低、去重先被挤掉、历史贡献以故障为主；
- 人手判断：MR-001~007 是文档平台路线图，solo 项目养不起第二个产品；
- 蒸馏问题（文档→memories）与移除正交：只需 LLM 提取 + 溯源字段，不需 RAG；
  是否值得做留 MR-019 独立评估；
- 外部调研判断：本 ADR 不需调研（范围收敛决策，证据全部在内部）；调研真正有价值
  的地方是推迟的蒸馏设计（mem0/Letta/Zep 文档入站模式），等 MR-019 启动时按
  RESEARCH_GUIDE 流程执行。

## 结论

文档 RAG 移出核心，文档角色收敛为记忆的可选入站源（待评估）。见 ADR-0010。

## 下一步

1. 实施 ADR-0010（删除清单单独排期，STATUS 跟踪）；
2. MR-019 评估蒸馏入站，做前按 RESEARCH_GUIDE 外部调研；
3. ADR-0009 检查点：服务可用后检索并修正"文档知识闭环/文档支柱"类过时记忆。
