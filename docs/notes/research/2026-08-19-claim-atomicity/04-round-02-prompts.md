## 说明

round-01 五平台已高度收敛到「粒度 = 可独立证伪单元；原子存储 + 聚合消费；整篇文档是证据不是结论」。
剩余 5 个决策点（组织层形态 / 证据引用精度 / 拆条质量保障 / 类型差异化粒度 / 提取成本控制）需要
在**我们的具体架构约束**下收敛。背景统一附在每节内，直接复制即可。

**项目内已拍板的约束（供平台参考，不要试图推翻）：**
- 对象模型：Evidence（不可再生、append-only）→ Claim（派生、可重算）→ Lineage Edge（谱系：supersedes/generalizes/contradicts/retract）；
- **Entity/主题（topic/tag）= P2 可选附属，不进核心 schema**（已拍板，一期不做实体网络）；
- Claim 字段：`statement`（适用条件折入句子）+ `claim_kind`（fact/preference/constraint/learned-pattern）+ `content_confidence`（单轴 Beta 期望）+ `scope`（项目作用域）+ `status`（派生物化缓存）；
- Claim 必须引用 ≥1 条 Evidence（claim_evidence 关系表，role 一期恒 support）；
- 召回 = 状态查询（预过滤 scope+active → 向量粗排 → 精排 相关×content）；
- 对账 = evidence 落库 → 异步 worker → 定位候选 → LLM 碰撞判定（CONFLICT/REDUNDANT/SUPPORT/UNRELATED）→ 单事务写。

## ChatGPT（侧重：落地执行 + 组织层形态定案）

```text
背景：我们在做一个 AI 开发助手的长期记忆系统，采用"证据/结论"两层模型：
- 证据（Evidence）：原始观察，追加式、不可修改、不可再生；
- 结论（Claim）：系统对证据理解+与其他结论碰撞后派生的主张，可重算；结论之间用谱系边
  （取代/泛化/矛盾/遗忘）表达演变；每条结论必须引用至少一条证据。
召回 = 状态查询（挑当前为真且相关的结论），用户可在工作台裁决（确认/纠正/遗忘）。

你的 round-01 回答我们非常认可，尤其"独立生命周期决定粒度"和"原子性与可理解性不要由同一个对象承担"。
我们已经确定要做"拆条"（一条证据 → 多条原子结论），但遇到一个实现决策需要你帮助收敛。

【问题 1：组织层形态】
你建议加 Group/Decision/Summary 作为 Claim 之上的组织层。但我们有一个已拍板的架构约束：
"Entity/主题（topic/tag）= P2 可选附属，不进核心 schema"，一期不做实体网络。
在这个约束下，如果一期就上"决策分组/主题分组"层，是否违背了这条拍板？还是说
"决策分组"和"主题/实体"是两回事，决策分组可以低成本先进核心？如果一期不加组织层，
靠现有谱系边（supersedes/generalizes/contradicts）和 scope 字段，能否扛住拆条后的碎片化问题？
请给一个"一期最小可行 + 二期演进"的路径建议。

【问题 2：拆条指令的落地版】
你 round-01 给了 extraction agent 的 instruction 草稿。请把它细化成一个可直接用的
结构化输出 JSON schema（约束：一次 LLM 调用，temperature=0，中文项目语境）：
- 输出字段建议（每条原子结论的 statement / claim_kind / 依赖关系怎么表达）；
- 如何处理"共同 scope/时间/条件"（你提的 qualifier 概念在 statement 文本里怎么折入）；
- 如何表达"多条原子结论同属一个决策事件"（在 JSON 里怎么留钩子，不新建实体表）；
- 如何在指令里防止两种失败：过度拆分（把因果/理由拆碎）与拆不干净（复合断言漏拆）。
请给出 JSON schema + 核心指令句（中文）。
```

- 证据（Evidence）：原始观察，追加式、不可修改、不可再生；

（一条证据 → 多条原子结论），落地依赖 LLM 一次调用输出 N 条原子断言。

你的 round-01 回答我们很认可，尤其"独立可证伪性测试"和"拆细代价的诚实标注"。
两个后续问题需要你帮助：

【问题 1：LLM 拆条的质量保障】
你引用的 FActScore 和 TriQua 都指出：原子性定义本身模糊，annotator 之间对
"合取结构怎么拆、指代与条件是否复制"有明显分歧。既然我们依赖 LLM 拆条（一次调用、temperature=0），
且拆错会导致错误粒度进入库（后续 supersede 都建立在错误粒度上）：
- 有没有低成本的"拆条质量校验"手段？比如让同一 LLM 做"反向合成检查"（把 N 条原子断言
  能否无损拼回原文）？还是抽检人工？还是监控指标（如平均拆出条数分布、单条长度分布）？
- 拆条质量差是"宁可漏拆（粗一点）"还是"宁可多拆（细一点）"？考虑到我们的裁决动作
  是整条 supersede，且存量要全部重建，这个取舍你怎么看？
- 拆条与"碰撞判定（CONFLICT/REDUNDANT/SUPPORT）"应该是一步 LLM 调用还是两步？
  一步的话输出结构怎么设计才不互相干扰？

【问题 2：提取成本控制（延迟提升）】
你 round-01 建议"候选原子结论先轻量挂在证据下，被复用命中/高风险时才提升为正式 Claim"。
我们当前实现是 evidence 落库后立即全量对账提炼（写路径不等待，worker 异步）。
如果一期做"延迟提升"，对"召回完整性"（新证据刚进来还没提升时，查询不到相关结论）有影响：
- 在我们这种"个人自托管 + 单 worker + evidence 量不大（每天几十条）"的规模下，
  延迟提升的收益是否值得复杂度？还是说先全量拆条、靠监控指标后置优化更务实？
- 如果坚持延迟提升，候选阶段的"轻量形式"在你的判断里应该是什么形态
  （存在哪、要不要 embedding、要不要参与对账）？
请把"来自文献/实践的事实"和"你自己的推理/综合"严格分开标注；不确定的直说不知道。
