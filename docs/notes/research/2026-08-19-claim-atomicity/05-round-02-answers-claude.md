## 问题 1：拆条质量保障

### 1a. 校验手段

**【文献】原子性定义本身模糊，这不是你们 prompt 写得不够好的问题，是这个任务本身在文献里就没有共识定义。**Schmidt et al.（"Dissecting Atomic Facts", 2025）的实证发现是：尽管原子事实在事实性评测里处于核心地位，却没有一个公认的定义；这种模糊性带来了实际后果——他们在标注实验里观察到人类标注者和 LLM 标注者之间存在显著分歧，尤其是在抽取事实的数量和粒度上，这些不一致说明了更深层的方法论缺口：如果标注的 ground truth 本身自相矛盾，事实正确性就无从评估。他们的结论是<cite index="57-1">低标注者间一致性（IAA）本身就是标注指南不完整或含糊的信号——</cite>这句话可以直接拿来用：**你们的"拆出条数分布"监控不是权宜之计，而是文献里认可的一种一致性诊断信号**，用于发现指南（prompt）哪里有歧义，而不是简单当噪声过滤掉。他们的具体做法是用语义相似度热力图和事实数量直方图做可视化分析，来迭代改进标注指南、消解标注者间分歧。

这给你们一个可落地的低成本方案：**不需要人工全量抽检，但需要把"分布异常"当作抽检触发信号**，而不是随机抽样。具体说——

**方案 A：分布监控 + 定向抽检（我认为是最省成本的第一层）**
监控每条证据拆出的条数分布、单条结论长度分布、单条结论引用证据 span 占原文比例。当某次拆分落在分布的尾部（比如条数明显偏多/偏少、单条长度明显偏长/偏短）时，才路由到人工复核，而不是均匀抽样。这是我从 Schmidt et al. 的方法直接迁移过来的推理，他们是在做标注质量分析工具，不是在做生产系统的在线质检，但诊断逻辑是通用的：分布尾部集中了大部分的粒度错误。

**方案 B：反向合成/往返校验（你自己提的思路，文献里有直接对应且已验证有效，但要注意它验证的是什么）**
这个技术在知识图谱抽取文献里已经有实现，不是你们独创。"Quadruple Shot"（arXiv:2508.03438）的做法是：系统拥有共指消解后的原句和抽取出的四元组，让 LLM 从四元组反向重建出共指句，再比较重建句和原句的语义相似度，用于量化二者的语义等价性，目的是缓解 LLM 幻觉出错误四元组的影响。另一篇（"Knowledge Restoration-driven Prompt Optimization", arXiv:2601.15037）用了几乎一样的机制但换成 NLI 判定：把抽取出的三元组通过知识还原模块转回自然语言句子，再用 NLI 模型判断还原句和原文之间是蕴含、中立还是矛盾。

**但这里有一个你需要注意的局限，这是我自己的推理，文献里没有直接讨论**：往返校验天然擅长抓**精度**错误（拼回去的东西和原文不一致，说明抽取时凭空加了/改了信息），但不擅长抓**召回**错误（原文里有一条信息，N 条结论里漏掉了，没人会拼出这一条不存在的东西去比对）。要用它检测"漏拆"，你得把 N 条结论**拼接后整体**和原文做语义覆盖度比较，而不是逐条比对——这是两个不同的检验，前者查"有没有编造"，后者查"有没有遗漏"，缺一个都不完整。

**方案 C：结构本身分流，减少歧义（来自 TriQua，值得认真考虑，可能比校验更根本）**
TriQua（arXiv:2608.05228）的思路是不强求所有事实都拆成统一粒度的简单三元组，而是简单主张抽取为标准三元组，复杂主张则表示为带辅助上下文限定符的超关系事实——这种自适应结构在不牺牲原子性的前提下保留了准确检索和验证所需的必要上下文。论文动机正是你们担心的那类问题：原子事实的细粒度在保留可验证主张更广泛的上下文时会丢失，然而上下文对准确验证往往是关键的——纯粹的"拆到最细"和"保留判断所需上下文"这两个目标本身有张力，没有被完全解决过。

我认为这个思路值得你们借鉴的地方在于：**与其让 LLM 在一次调用里自由决定"这句话该拆几条"，不如先做一次轻量分类——判断这条证据是"简单陈述"还是"复合决策"，再用不同的输出 schema**。简单陈述直接输出单条 claim；复合决策输出"主 claim + 若干限定符/子属性"的结构化形式,而不是拆成完全独立、互相看不出关联的 N 条平行结论。这样部署选型那个例子会变成一条主结论"部署方案确定"下面挂着 4 个可独立修改的字段（选型/上限/分类数/阶段数），而不是 4 条互相无引用关系的独立结论——**既满足了你们"独立可裁决"的要求（每个字段可单独 supersede），又不丢失"这 4 件事同属一次部署决策"这个上下文**，某种程度上也回应了我 round-01 提的"co-derived-from 分组边"那个补丁，只是把分组关系直接建在数据结构里而不是靠额外的谱系边。这是我把 TriQua 的思路和你们已有模型嫁接后的推理，TriQua 论文本身是做事实核查评测，不是做记忆系统，这个迁移没有被验证过。

### 1b. 宁可漏拆还是宁可多拆

**【推理，这条文献没有直接讨论，是我基于你们系统特有约束的判断】**

我倾向于：**宁可多拆一点，不要漏拆**，理由不是"细一点总是更好"（round-01 已经说明拆太细有代价），而是一个**错误可恢复性的不对称**：

- 拆粗了之后想拆细：证据不可变，理论上可以重新对同一份证据跑一次更细的抽取。但麻烦在于——**旧的、按粗粒度产生的用户裁决历史（用户已经确认过的那条粗结论）没法自动映射到新拆出的细结论上**。你相当于要么把旧确认记录作废重新走一遍确认流程，要么手工建立粗结论到细结论的映射关系。这是真实成本，而且是你已经点出来的"存量要全部重建"。
- 拆细了之后想合并：这个操作路径更干净。你已经有谱系边机制，加一类"合并"边（或者把已有的"泛化"边语义扩展一下）把两条经常同时出现、从未单独被纠正过的原子结论合并成一条更粗的展示单位，**不需要动底层证据引用，也不需要让用户重新确认**——因为两条细结论各自的确认记录仍然有效，只是在展示/召回层面被组装到了一起。

所以这不是"细的错误代价更小"，而是"细的错误在你们这套谱系边架构下，修复路径不破坏已有的用户裁决历史；粗的错误修复路径会破坏"。这个判断依赖一个前提：你们的合并操作确实能做成不影响已有 confirm 记录的样子——如果做不到，这个不对称论证就不成立，这点需要你们在设计合并语义时验证。

需要提醒的是，这个建议是"存疑时偏向拆"，不是"能拆多细就拆多细"——round-01 提到的拆细代价（自足性丢失、对账开销、召回噪音）依然成立，只是在两难边界情形下，我认为该往哪边倒有一个可以讲清楚的理由，而不是纯凭直觉。

### 1c. 一步还是两步

**【文献】结构上有证据支持不要一步做完，而且不完全是"质量更好"的问题，是"数据依赖关系"的问题。**"Fact in Fragments"（AFEV, arXiv:2506.07446）的动机之一是静态的一次性分解策略会导致误差累积，因此该框架采用迭代式原子事实抽取策略，利用先前已验证原子事实的理解来指导后续分解过程，确保随着迭代推进分解更连贯。另有综述性总结指出最优分解是输入复杂度、下游验证器强度、原子性与覆盖度取舍需求的函数；自适应分解（比如根据输入长度动态设定子主张数量）配合基于元提示的错误反思，能带来最佳的实证效果。这两条都指向同一个方向：**分解和后续验证/判断如果糅在一次不加区分的调用里做，误差没有机会被中间步骤发现就直接进入下一步**。

**【推理】更根本的是一个结构性限制，不是"最好分两步"的偏好问题，是"不可能一步做完"：** 碰撞判定（CONFLICT/REDUNDANT/SUPPORT）需要拿新结论去和**已经在库里的**结论比较，而已存结论在 LLM 这次调用开始时是不在它上下文里的（除非你们把整个结论库都塞进 prompt，那不现实）。所以碰撞判定天然依赖一次检索——用新拆出的结论去做 embedding/实体键查询，找出候选相关的已有结论，再拿这些候选去做冲突判断。**这一步检索必须发生在"知道新结论长什么样"之后**，也就是说拆条必须先跑完，你才知道该拿什么去查。这不是设计选择，是数据依赖顺序决定的：拆条(LLM 调用1) → 检索候选(embedding/实体键查询，非LLM) → 碰撞判断(LLM 调用2，输入是新结论+检索到的候选)。

如果想省成本，可省的地方是把"调用2"做成批处理——一次调用里把这条证据拆出的 N 条结论，连同各自检索到的候选冲突项，一起传入，输出按 claim_id 索引的判断结果数组，而不是每条结论单独发一次请求。输出结构上，我建议第一步（拆条）的输出**不要包含任何冲突/支持字段**——因为这一步 LLM 没有看到已存结论，让它在这时候猜"这条大概会不会和已有的冲突"是在要求它回答它没有依据回答的问题，这正好命中你自己担心的"结构互相干扰"：拆条阶段的任务是"这条证据里有几个独立可证伪的判断，各自完整表达是什么"，混入它回答不了的冲突判断字段，只会让两个任务互相拉低质量。

## 问题 2：延迟提升值不值

**【文献】生产实践里，"异步"这个词通常指的是"延后重的整理/去重/合并工作"，而不是"延后基本的事实抽取本身"。** Letta 官方博客描述的模式是：睡眠时计算（sleep-time compute）让模型能在系统空闲时"思考"，这从根本上要求有状态的智能体——即维护随时间持续存在的记忆或上下文的系统。另一篇对该模式的转述更具体：智能体实时用已有的信念作答；会话结束后，后台进程异步抽取新信念、消解冲突、标记需要人工复核的内容；下次会话时更新后的信念才可用——用新知识稍延迟一点的整合，去换取零延迟的智能体响应，是值得的权衡。而针对具体分工，另一份总结说得更直接：大多数生产系统对偏好类信息的抽取采用写入时（on-write）处理，对无法预判的复杂多跳推理采用读取时（on-read）处理；共识是重的整理工作（重新摘要、图重构、冲突消解）必须异步——在对话轮次结束后于后台worker运行,这样才能保持用户侧延迟低；由此带来的隐含代价是，永远存在一个窗口期，新写入的信息还没被反映进整理后的记忆库中。

**这条文献信息让我要修正 round-01 那个建议的适用范围**：round-01 说的"候选先轻量挂着，被复用/风险命中才提升"，本质上是在说"要不要延后**抽取**本身"；而文献里普遍验证过、成熟的模式是"抽取本身写入时就做（因为便宜），延后的是**去重/合并/图重构**这类真正贵的整理工作"。这是两个不同的延迟点，我在 round-01 没有把它们分清楚。

### 2a. 在你们的规模下，值不值得

**【推理】我认为答案是：不值得，先按你们现在的"写路径不等待、worker 异步全量拆条对账"做，理由如下：**

round-01 担心的成本（对账计算量随结论数超线性增长、存储膨胀）是在**结论数量和证据吞吐都变大**之后才会体现出压力的问题。你现在的规模是个人自托管、单 worker、每天几十条证据——按这个量级，就算每条证据都拆成 4-5 条原子结论，一天也就一两百条 LLM 调用量级的抽取+对账工作，单 worker 异步处理完全跑得动，也谈不上"召回完整性"上有实质的窗口期问题，因为你现在这套"证据落库后立即异步全量提炼"本身就是文献里那个成熟模式（Letta 的 pattern），差别只是你们对账也做了全量而不是分层，但对账全量在这个证据密度下不构成瓶颈。

延迟提升要解决的问题（对账计算量、存储、噪音）目前对你们来说都不是真实存在的瓶颈，加这层"候选/正式"两级状态机的复杂度（要多维护一个状态字段、一套提升触发规则、提升事件本身的一致性）在收益不明确的情况下是纯粹的负担。**更务实的路径确实是你自己提的"先全量拆条，靠监控指标后置优化"**——把 1a 里提到的分布监控先跑起来，同时记录一个更直接的指标：**worker 处理证据到结论落库可用的端到端延迟、以及每次对账实际发生的比较次数**。等这两个指标真的显现出增长趋势（比如证据量涨到每天几百条，或者对账比较次数明显超线性），再回头做分层提升不迟——而且到那时候你会有真实的分布数据去决定"复用信号"和"风险信号"具体该怎么定义阈值，现在凭空设计这套触发规则，参数基本靠猜。

这个判断本身没有文献直接支持"在这个具体量级下不该做延迟提升"，是我按数量级做的工程判断，你们如果对未来扩容有明确预期（比如很快会有多用户/团队场景），这个判断的前提就不成立了，需要你们按自己的路线图评估。

### 2b. 如果还是要做，候选层的形态

**【推理，无直接文献先例，是从 A-MEM 的笔记式结构和 Graphiti 的实体键存储范式推出来的类比】**既然明确了 round-01 那个设计其实是在说"要不要延后抽取"这个更少见、成熟度更低的模式，如果你们仍然想做，我建议候选层要严格做到"不产生本该被延后的那部分成本"，否则这层就白设计了：

- 候选结论**不生成 embedding、不写入图的实体索引**——生成 embedding 和插入实体图节点正是你们想推迟的那部分成本，候选层如果连这个都做了，就等于没有延迟任何东西。
- 候选结论以结构化 JSON 形式挂在触发它的证据 ID 下即可，携带拆条阶段（本来就要做，这步无法省）已经产出的实体/谓词标签，但不参与检索、不参与对账。它存在的唯一作用是**缓存**——避免提升发生时要重新对同一份证据跑一次抽取 LLM 调用。
- 提升事件 = 补跑 embedding 生成 + 插入图节点/实体索引 + 针对同实体键的既有结论跑一次对账（复用你们已有的、按实体分桶缩小比较范围的机制）。
- 召回缺口是真实存在且无法完全避免的：候选没被索引，语义/状态查询就是查不到它,这个代价在 round-01 已经点明过，这里没有新的规避手段，只能说如果风险信号可以做成廉价的关键词/模式预筛（不需要语义分类器），可以让一部分高风险候选跳过"候选"状态直接提升，缩小缺口覆盖的范围,但这仍然是启发式的，覆盖不了所有场景。

这部分设计我没有找到任何论文或工程实践专门讨论"个人规模记忆系统里候选结论该以什么形态存在"这个问题，是我把 A-MEM 的笔记结构思路和 Graphiti 的实体键限域策略拼起来的推断，没有被验证过，如果你们真走到需要做这个的规模，建议先小范围灰度、拿真实召回缺口数据核实这套设计是否真的解决了问题。
