## 回答原文

**裁决结论先给出，再展开理由。**

### 问题 1：一期是否加分组层
**裁决：选 B（一期不加任何持久化分组层），靠谱系边 + scope + 召回时动态聚合扛住。个人自托管规模（几百条结论）下足够。**

**理由与取舍：**
- 一期明确不做 Entity/主题实体网络（P2）。任何落库的 `group_id` 或关系表，本质上是轻量主题/决策实体的雏形，会与“P2 不进核心”的拍板产生语义与实现张力。一旦加了，后续很容易被自然扩展成半实体网络，增加迁移与一致性成本。
- 现有机制已具备足够组织力：
  - 谱系边（取代 / 泛化 / 矛盾 / 遗忘）可表达演变与部分聚合关系。
  - scope（项目 / 会话 / 用户级）提供天然边界。
  - 召回是状态查询，可在查询时按语义相似度、时间、谱系邻近、关键词/embedding 聚类做动态聚合，而不必落库。
- 个人自托管规模（几百条结论）下，动态聚合的计算与索引成本极低，完全可接受。碎片化风险主要体现在“人类工作台可读性”和“注入时连贯性”，而非系统正确性。这两点可通过召回后排序 + 轻量提示词重组解决，无需持久化分组。
- 关于 round-01 的“受控复合层”：在“复合结论不参与谱系演化、纠正一律落到原子层”的前提下，它**基本等价于 B**。复合层若存在，也只是召回时的临时视图（runtime composition），而非存储层的一等公民。这样既保留了原子结论的可纠正性与证据诚实性，又避免了持久化分组带来的 P2 越界风险。

**最小演进路径建议（仅作参考，非强制）：**  
若后续实际使用中发现动态聚合经常失败（例如同一决策簇的原子结论频繁被拆散召回），再考虑加一个极轻量的、只读的 `topic_hint` 字符串字段（非外键、非关系表），仍保持非核心地位。一期坚决不加。

### 问题 2：claim_kind 是否需要差异化粒度
**裁决：不必要做类型级别的硬差异化粒度上限。统一以“可独立证伪 / 可独立被证据支持或推翻”为判据即可覆盖四类差异。**

**理由：**
- 四类结论（fact / preference / constraint / learned-pattern）的本质差异在于**语义性质与裁决权重**，而非“可拆分性”本身。
  - fact：客观断言，最适合原子化。
  - preference：主观偏好，天然较原子（“喜欢 X”很少需要再拆）。
  - constraint：硬性约束，通常原子且高优先级。
  - learned-pattern：实践教训，可能稍复杂，但仍可拆成“在什么条件下，采用什么做法，因为什么结果”。
- “可独立证伪”判据已经足够通用：一条结论是否还能被进一步拆成两个都能独立被证据支持/推翻的命题？若能，就拆；若拆后失去独立意义或引入幻觉，就不拆。这个判据对四类都适用，无需再叠加类型级上限。
- 强行按类型设定不同原子度/长度上限，会增加提取逻辑复杂度，并在边界案例（例如一条 constraint 带有条件从句）上产生人为不一致。Gemini 建议的权重/层级字段更适合作为召回排序或裁决优先级信号，而非粒度控制手段。
- doubao 提到的“架构/方案结构化子项”在你们当前 4 值体系中并不存在独立类型，强行映射会扭曲模型。

**统一粒度策略（适用于全部 4 类）：**
- **原子度要求**：默认拆到“最小可独立证伪的有意义命题”。合取结构强制拆；强依赖（条件、限定、时间范围）保留必要上下文，使结论自包含。
- **是否允许复合**：不允许持久化复合结论参与谱系演化。召回时可临时组合，但纠正与遗忘一律落到原子层。
- **statement 长度参考**（经验区间，非硬限制）：
  - 理想：15–80 字（中文）或等效英文 token。
  - 可接受上限：约 150 字。超过此长度且仍可拆分时，优先拆。
  - 极短（<10 字）若语义完整也接受（例如明确的 preference 或 constraint）。
- **类型间的软差异（仅作提取提示，非硬规则）**：
  - fact / constraint：更积极拆分，强调客观可验证性。
  - preference：通常已很原子，少拆。
  - learned-pattern：允许稍长一点以保留“条件–做法–结果”的最小完整结构，但仍优先拆成可独立引用的部分。

**补充建议（与粒度正交）：**  
可为 `claim_kind` 增加或强化召回/裁决时的权重与优先级（例如 constraint > fact > learned-pattern > preference），这比差异化粒度更直接有用，且不增加存储与提取复杂度。

---

**总结取舍逻辑**：一期优先保持核心模型简洁（证据不可变 + 原子结论 + 谱系边 + 状态查询），把组织与组合责任尽量放在召回与注入层。这样既兑现了细粒度的收益，又严格遵守“Entity/主题 P2 不进核心”的边界，同时避免过早引入难以回退的持久化结构。个人规模下动态聚合完全够用；若未来规模或使用模式证明不足，再最小化补充分组信号。
