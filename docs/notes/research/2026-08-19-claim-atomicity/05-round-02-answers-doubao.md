## 问题 1：证据片段引用的工程落地

### 1.1 中文文本 span 定位的具体坑

**【实践】** 中文 RAG 工程界对 RecursiveCharacterTextSplitter 的中文缺陷有比较一致的总结，直接映射到你们的 span 引用场景：

| 坑 | 具体表现 | 对 span 引用的影响 |
|---|---|---|
| **无空格分词** | 中文没有天然词边界，字符偏移容易截断在词中间（如"部署选型"被切成"部署选"+"型"） | LLM 输出的 start/end 如果落在词中间，截取出来的文本是残片 |
| **默认分隔符是英文的** | LangChain 默认 `separators=["\n\n", "\n", " ", ""]`，完全不识别中文句末标点 `。！？；` 和分句标点 `，、：` | 长句被强制按字符截断，span 边界不在语义边界上 |
| **列表结构割裂** | 多级列表（`1. xxx 2. xxx`）中，单条列表项容易被拆到两个块 | 一条结论引用的列表项可能跨两个 span，定位困难 |
| **标题与正文剥离** | Markdown 标题 `## xxx` 和正文被拆到不同块 | 结论引用正文时丢失标题上下文，不知道这条规则属于哪个章节 |
| **chunk_overlap 对中文无效** | 重叠机制依赖英文空格边界，中文重叠要么截断在词中间，要么产生无意义重复 | 用 overlap 做"容错窗口"在中文里不可靠 |
| **隐藏字符/零宽字符** | `\u200B` 等零宽空格、BOM 头会破坏逻辑文本索引与视觉位置的一致性 | 你算的 char offset 和用户看到的位置对不上 |
| **BERT 类分词器空格痕迹** | 中文 BERT 分词器把每个字当独立 token，解码时默认在 token 间加空格 | 如果你的证据经过模型 tokenize→detokenize 再存储，原文会被插入空格，span 全部偏移 |

**【推理】** 最后一条最容易被忽略：如果你们的证据在入库前经过任何 LLM 处理（比如清洗、格式化），一定要确保存储的是**原始字节流**，而不是模型输出的文本。否则 span 引用从根上就是错的。

### 1.2 方案 A（LLM 拆条顺带输出 span）可行吗？

**【推理】** 可行，但**不能直接信任 LLM 输出的数字偏移**，必须做后校验。原因：

1. LLM 对长文本的字符计数天生不精确——中文一个字是一个 char，但模型可能按"词"或"语义块"估算位置，几百字的文本偏移误差 5-20 个字符很常见。
2. LLM 输出的 span 经常包含"大概是这一段"的模糊引用，而不是精确的起止位置。

**【推理】MVP 做法——让 LLM 输出"引用原文子句"而不是"数字偏移"：**

```
拆条 Prompt 输出格式：
{
  "claim": "部署选型偏 Miniflux",
  "evidence_quotes": [
    "我们最后选了 Miniflux 作为自建 RSS 服务"
  ]
}
```

系统拿到 `evidence_quotes` 后，用**字符串精确匹配**在证据原文中定位，算出 `start_char` / `end_char`。匹配失败时降级处理（见 1.4）。

这个方案的好处：
- LLM 只需要复制粘贴原文，不需要计数，准确率高很多。
- 匹配过程是确定性的，结果可复现。
- `quoted_text` 本身可以直接展示给用户做溯源高亮。

### 1.3 方案 B（先分块再逐块拆条）更稳吗？

**【推理】** 更稳，但分块的目的不是 RAG 检索，而是**给拆条提供稳定的引用单元**。

**【实践】** 中文分块的工程推荐参数（多篇 RAG 实践文章一致）：

```python
# 中文专属分隔符优先级（把中文标点提升到高优先级）
chinese_separators = [
    "\n\n",           # 段落
    "。", "！", "？", "；",  # 句末标点
    "，", "、", "：",        # 分句标点
    "\n", " ", ""     # 兜底
]

# 参数
chunk_size = 300-500  # 中文字符，比英文小（中文信息密度高）
chunk_overlap = 10-15% of chunk_size  # 30-75 字符，不要更大
```

**【实践】** 对于 Markdown 结构化文档（你们的项目架构文档很可能是这种），推荐**先按标题分层，再用中文递归兜底**：

```
1. 用 MarkdownHeaderTextSplitter 按 ## / ### / #### 拆分
2. 每个标题块内，用中文标点递归切分器微调
3. 每个 chunk 携带 header_path（如 ["部署方案", "信息源策略"]）
```

这样拆出来的 chunk 自带章节上下文，结论引用 chunk_id 时，即使不展开 span，也知道这条结论来自哪个章节。

**【推理】** 块粒度怎么定？我的建议是 **300-500 中文字符**，理由：
- 太小（<200）：块数量爆炸，拆条 LLM 调用次数多，且单块上下文不足，LLM 可能误解句子含义。
- 太大（>800）：回到了"整条证据"的问题，块内仍然可能包含多个独立命题，span 定位的收益被稀释。
- 300-500 大概是 1-3 个完整段落，或 5-10 条列表项，足够 LLM 理解上下文，又足够精确。

### 1.4 推荐的 MVP 方案（混合方案）

**【推理】** 不要二选一，用"分块 + 子句引用 + 字符串匹配"的三层方案：

**数据结构：**

```sql
-- 证据分块表（新增）
CREATE TABLE evidence_chunk (
    chunk_id      TEXT PRIMARY KEY,
    evidence_id   TEXT NOT NULL REFERENCES evidence(id),
    chunk_index   INT  NOT NULL,          -- 在证据中的序号
    start_char    INT  NOT NULL,          -- 在证据原文中的绝对偏移
    end_char      INT  NOT NULL,
    header_path   TEXT,                    -- Markdown 标题路径，如 "部署方案/信息源"
    content       TEXT NOT NULL            -- 块内文本（冗余存储，方便检索）
);

-- 结论-证据引用表（升级）
CREATE TABLE claim_evidence (
    claim_id      TEXT NOT NULL REFERENCES claim(id),
    evidence_id   TEXT NOT NULL REFERENCES evidence(id),
    chunk_id      TEXT REFERENCES evidence_chunk(chunk_id),  -- 可空，兼容旧数据
    start_char    INT,                     -- 在证据原文中的绝对偏移
    end_char      INT,
    quoted_text   TEXT NOT NULL,           -- LLM 输出的原文子句，用于校验和展示
    match_status  TEXT NOT NULL DEFAULT 'chunk'  -- exact / fuzzy / chunk / failed
);
```

**流程：**

1. **证据入库** → 立即做中文语义分块 → 写入 `evidence_chunk`。
2. **拆条** → 逐块送入 LLM（而不是整条证据），LLM 输出结论 + `evidence_quotes`（原文子句）。
3. **定位** → 系统在**对应 chunk 内**用 `quoted_text` 做字符串精确匹配，算出 `start_char` / `end_char`。
4. **校验与降级：**
   - 精确匹配成功 → `match_status = 'exact'`
   - 精确匹配失败，用编辑距离模糊匹配（相似度 > 0.9）→ `match_status = 'fuzzy'`，记录偏移
   - 模糊匹配也失败 → 降级为 `chunk_id` 级引用，`match_status = 'chunk'`，`start_char/end_char` 留空
   - 连 chunk 都不确定 → `match_status = 'failed'`，这条结论标记为"溯源待人工确认"

**为什么在 chunk 内匹配而不是整条证据内匹配？**
- chunk 内文本短（300-500 字），匹配速度快，歧义少。
- 同一句话在整条证据中可能出现多次（如"Miniflux"在文档里出现 5 次），chunk 内通常只出现 1 次。
- 即使匹配失败，降级到 chunk 级也比降级到 evidence 级精确得多。

### 1.5 国内产品的溯源精度现状

**【实践】** 我查到的情况：

- **企业级 AI 知识库**（如苏哒智能等）：做到**文档名 + 页码 + 段落片段**级，点击引用高亮原文段落。但这是 RAG 场景，引用单元是检索命中的 chunk，不是"结论→证据子句"的精确映射。
- **通义千问"引证"功能**：政策新闻类提供核查入口，标注官方信源，红绿标区分可信度。精度到"文章/来源"级，不到句子级。
- **MemOS + HaluMem**：记忆张量联合中国电信研究院发布的记忆幻觉评估框架，号称具备"自检"与"溯源"能力。但公开资料只提到将记忆过程拆分为抽取/存储/检索三阶段评估，**没有公开溯源精度的具体实现或指标**。【不确定】他们内部是否做到了子句级引用。
- **豆包/百度等通用助手**：知识图谱 + 事实校验，多源交叉验证，但这是事实核查层面，不是记忆系统的证据溯源。

**【推理】** 总的来说，**国内产品在"结论→证据片段"的精确溯源上，公开可见的最高精度是段落/chunk 级，很少见到子句级（span 级）的成熟产品**。这意味着你们如果做到 span 级，在工程上是有差异化的，但也意味着可借鉴的现成方案少，坑要自己踩。

### 1.6 "引用整条证据但只被一句支撑"的可信度失真案例

**【实践】** 这在 RAG 场景中是已知问题，有个专门的叫法叫"**证据过度包含**"（over-evidencing）或"**支撑范围膨胀**"。

具体表现（推理 + 实践综合）：
- 检索命中一个 500 字的 chunk，其中只有一句话支撑答案，但模型把整个 chunk 都当作"参考资料"注入上下文。
- 用户看到"引用了 3 个来源"，觉得很可信，但实际上 3 个来源加起来 1500 字里只有 3 句话相关。
- 在你们的记忆系统里，这个问题更严重：**结论的可信度评分如果基于"引用了多少条证据"或"引用证据的总长度"，就会被根本没写出来的内容抬高**——这正是你 round-0 描述的问题。

**【推理】** 解决这个问题的关键是：**可信度计算必须基于 span 级引用的实际内容，而不是 evidence_id 级**。具体来说：
- 一条结论引用了 evidence A 的 15 字 span，和引用了 evidence A 的 2000 字全文，可信度权重应该不同。
- 可以用 `quoted_text` 的信息密度（是否包含具体数字、专有名词、决策动词）来加权，而不是简单计数。

## 问题 2：批量演化 / 延迟整合的工程形态

### 2.1 立即拆条 vs 批量整合：你们的规模该怎么选

**【推理】** 先厘清一个概念：**"拆条"和"整合/演化"是两件事，不应该绑定在一起。**

| 操作 | 范围 | 成本 | 时效性要求 |
|---|---|---|---|
| **拆条** | 单条证据内，提取原子结论 | 低（1 次 LLM 调用/证据） | 高（用户马上可能问到） |
| **整合/演化** | 跨证据，对账、矛盾检测、合并、泛化、建谱系边 | 高（需要对比多条结论） | 低（晚几小时做不影响） |

**【推理】** 对于个人自托管、每天几十条证据的规模：
- **拆条应该立即做**。每天几十条证据，每条 1 次 LLM 调用，成本完全可承受。而且拆条是单证据内操作，不需要跨证据上下文，立即做没有技术障碍。
- **整合/演化应该批量做**。跨证据对账需要加载多条相关结论，每条新证据都立即做一次全库对账是浪费——第 1 条证据来的时候没有东西可对，第 2 条来的时候只需要对 1 条，第 10 条来的时候对 9 条……累计成本是 O(n²)，批量做是 O(n)。

**【实践】** 这个"快速写入 + 慢速整合"的双通道架构，在多个系统中都有体现：
- **Auto-Dreamer 论文**：Fast Online Acquisition（冻结的 writer 模型逐条处理，append-only，不做跨会话比较）+ Slow Offline Consolidation（学习型 consolidator 离线做区域重写）。
- **Google Cloud Always-On Memory Agent**：ConsolidateAgent 跑在定时器上，默认每 30 分钟，审查未整合记忆、找连接、写合成摘要。
- **LeanMem**：事件记忆先进入缓冲区立即可检索，缓冲区达到容量后触发延迟整合，只更新局部相关事件。

### 2.2 批量整合的触发条件怎么定

**【实践】** 各产品的触发策略：

| 产品/系统 | 触发条件 | 来源 |
|---|---|---|
| Claude Code Auto Dream | 积累 5 个新会话 + 至少 24 小时 | 第三方分析 |
| dream-memory (GitHub 开源) | `min_sessions_between_dreams=3` AND `min_hours_between_dreams=1.0` | GitHub README |
| Google Cloud Always-On Memory | 固定定时器，默认 30 分钟 | 技术博客 |
| AgentScope Java | 后台异步节流任务，低频周期性执行，整体重写 MEMORY.md | 源码分析 |
| LeanMem | 事件缓冲区达到预设容量后触发 | 论文 |
| 通用 Agent 实践 | 批量整合按计划运行，高量用户才需要；异步写入在响应交付后 | MindStudio 工程博客 |

**【推理】** 对于你们的个人自托管场景，推荐**混合触发（OR 逻辑）**：

```
触发整合的条件（满足任一即触发）：
1. 未整合结论数 >= 10 条   # 条数阈值，保证批量有足够内容
2. 距上次整合 >= 2 小时      # 时间阈值，保证即使条数少也能定期整合
3. 系统空闲（CPU < 20% 且无活跃对话）且未整合结论数 >= 3  # 空闲时提前做
```

参数选择理由：
- **10 条**：个人每天几十条证据，拆条后可能产生 50-100 条原子结论。10 条大概是 1-2 小时的产出量，批量处理时 LLM 可以一次对比 10 条结论，成本摊薄。
- **2 小时**：个人使用场景下，2 小时内的"召回缺口"影响不大——用户不太可能在说完一件事 2 小时内就问到需要跨证据对账才能回答的问题。
- **空闲触发**：自托管机器通常有大量空闲时间，利用空闲提前整合可以降低峰值时的等待。

**【推理】** 不推荐的触发方式：
- **每条证据后立即整合**：O(n²) 成本，且早期证据少的时候整合没有意义。
- **固定长周期（如每天一次）**：如果用户某天密集输入 100 条证据，当天内召回缺口太大。
- **纯条数阈值（没有时间兜底）**：如果用户很久不用，少量未整合结论永远不被整合。

### 2.3 召回缺口怎么补

**【推理】** 核心思路：**未整合的结论不是"不存在"，而是"状态为待整合"，仍然可以被召回。**

具体方案：

```
结论状态机：
pending       — 拆条完成，未参与整合，可召回，可信度权重 ×0.8
consolidated  — 已整合，已建谱系边，可召回，正常可信度
superseded    — 被取代，不召回
forgotten     — 被遗忘，不召回
```

**召回时同时查两个池：**
1. **已整合结论池**（status = consolidated）：高质量，有谱系边，可信度高。
2. **待整合结论池**（status = pending）：立即可用，但可能存在未检测到的矛盾/重复，可信度略低。

召回结果合并后，按相关性 + 可信度排序。pending 结论可以正常使用，但在工作台 UI 上可以标记"待整合"状态，让用户知道这条结论还没经过跨证据对账。

**【实践】** 这个思路和 LeanMem 的"事件缓冲区立即可检索"完全一致——新事件先进入缓冲区，立即可被检索，缓冲区满了才批量整合。

**【推理】** 额外的兜底措施：
- 如果用户的问题明确涉及"刚说的内容"（比如用户说"刚才我们讨论的部署方案"），召回时**强制包含最近 N 条 pending 结论**，不管语义相似度如何。
- 可以在对话层面保留最近 10-20 轮的原始上下文（短期记忆），这部分不需要走长期记忆召回，直接注入。

### 2.4 整合阶段具体做什么

**【推理】** 批量整合不是简单的"合并重复"，应该包含以下操作，按优先级排序：

1. **矛盾检测**：对待整合结论，按主题/实体聚类，在每个聚类内检测矛盾（如"信息源 ≤20" vs "信息源 ≤30"）。检测到矛盾不自动解决，标记为 `conflict_pending`，推给用户裁决。
2. **重复合并**：语义高度相似（embedding 相似度 > 0.95）且无矛盾的结论，合并为一条，保留所有证据引用。被合并的结论标记为 `superseded`，谱系边指向合并后的结论。
3. **泛化提炼**：多条具体结论如果共享同一模式（如"项目 A 用 PostgreSQL"、"项目 B 用 PostgreSQL"），可以提炼出泛化结论（"用户偏好 PostgreSQL"），但**泛化结论必须引用所有支撑它的具体结论**，且标记为 `generalized`，可信度低于原始具体结论。
4. **谱系边建立**：在新结论与已有结论之间建立取代/泛化/矛盾边，确保演变可追溯。
5. **可信度重算**：整合完成后，对受影响的结论重新计算可信度（基于 span 级证据引用的数量和质量）。

**【推理】** 整合的 LLM 调用方式：不要一次把所有待整合结论塞给 LLM（可能几十条，上下文太长），而是**按主题聚类后逐簇处理**——每簇 5-10 条相关结论，一次 LLM 调用处理一簇。这样每簇的上下文可控，且 LLM 可以专注于对比相关内容。

### 2.5 中文生态里值得借鉴的记忆整合产品

**【实践】** 我查到的国内/中文生态相关产品：

1. **MemOS（记忆张量 + 上海交大 + 人大 + 同济 + 浙大 + 中国电信研究院）**
   - 三层架构：API 层 / 调度管理层（MemScheduler）/ 存储层

   - **【不确定】** 公开资料没有详细说明"记忆整合"的具体触发条件和处理流程，更多是架构层面的描述。

## 总结：两个问题的最小可行方案速查

### 问题 1 MVP
1. 证据入库 → 中文语义分块（300-500 字，中文标点优先级分隔符，Markdown 先按标题分层）。
2. 逐块拆条，LLM 输出结论 + `evidence_quotes`（原文子句，不是数字偏移）。
3. 在 chunk 内用字符串匹配定位 span，匹配失败逐级降级（exact → fuzzy → chunk → failed）。
4. 可信度计算基于 span 级引用的实际内容，不是 evidence_id 计数。

### 问题 2 MVP
1. **拆条立即做**（单证据内，低成本，高时效），**整合批量做**（跨证据，高成本，低时效）。
2. 整合触发：未整合结论 ≥10 条 OR 距上次 ≥2 小时 OR 系统空闲且 ≥3 条。
3. 召回缺口：pending 结论立即可召回，可信度 ×0.8，UI 标记"待整合"；最近对话强制包含 pending 结论。
4. 整合按主题聚类逐簇处理（每簇 5-10 条），操作优先级：矛盾检测 → 重复合并 → 泛化提炼 → 谱系边 → 可信度重算。

最后说一个**【不确定】**的点：上述方案中的具体参数（chunk_size=300-500、10 条触发、2 小时、可信度 ×0.8）都是基于行业实践和推理的**初始值**，实际效果需要你们用自己的语料做 A/B 测试调优。特别是中文分块的参数，不同类型的文本（对话 vs 文档 vs 代码注释）最优值可能差异很大。
