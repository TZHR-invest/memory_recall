整体：综合推理，结合 Agent 记忆工程实践、产品交互风险；引用前文已提到的 Generative Agents、OpenAI Agent Memory 博客、ADR 范式。新增的分级置信度、复用触发升级属于工程推演，无直接文献。
问题 1：候选闸门的用户疲劳风险 + 置信度分级、差异化确认强度
核心风险预判：
强制弹窗式 “是否保存卡片？保存 / 跳过”，高频开发场景下一定会出现确认疲劳：
高频踩坑调试时，每解决一个报错就弹确认，打断开发流；
用户进入机械行为：无脑点跳过，有用经验全部流失；或者无脑点保存，大量低质量候选全部入库，重新回到记忆污染。
闸门本身没错，但“统一强度的显式确认” 是负担来源，不是闸门本身。
所以不能一刀切：全部要用户确认，或者全部自动落库。解决方案就是候选置信度分级，匹配差异化确认强度，把 “强制弹窗确认” 降级为少数场景使用。
第一步：给沉淀候选打置信度分数（内部模型打分，对用户不可见）
对 AI 生成的沉淀草稿卡片，内部计算置信度，不是一个单一数值，由几类信号加权：
高置信度（高可能性是有效可沉淀知识）
信号：
会话闭环：完整复现问题 → 定位根因 → 给出解决方案 → 用户验证生效（用户反馈好了、修复成功，不是 AI 自说自话）；
模式特征：已经从单次实例提炼成模式，不是绑定本次文件路径、本次报错行号；
低噪声：不含大量吐槽、临时实验、废弃尝试；
无强项目专属绑定：不高度耦合本项目独有的业务逻辑。
例子：通用构建报错排查、某工具的通用坑点。
中置信度
信号：已经形成卡片草稿，但存在不确定性：版本边界模糊、部分条件缺失、明显绑定当前项目业务。
例子：本项目内部一套组件封装方案，不确定是否适合别的项目。
低置信度
信号：高度绑定本次会话实例、大量临时试错、没有经过用户验证成功、混杂大量发散闲聊。
例子：单次调试输出、失败的临时尝试。低置信直接丢弃，不进入候选池。
第二步：分级匹配不同确认强度（三种档位，不只有 “弹窗确认”）
1）高置信度候选：静默候选，不阻塞主对话流（无强制弹窗）
行为：草稿卡片写入临时候选池（不进入检索库，不参与记忆召回），对用户无阻断弹窗；
触达方式：非侵入式 UI：侧边栏 / 会话末尾折叠面板，汇总本次会话全部高置信候选；
用户动作完全自由：有空就批量审阅，批量保存到项目记忆；批量删除；完全忽略也不会自动入库。
不会打断编码流，避免机械点击。用户疲劳时可以完全无视，不会自动产生记忆污染。
2）中置信度候选：轻量可选提示，可一键忽略
行为：简短行内提示，不弹窗：【建议沉淀】本次踩坑可整理为项目经验卡片 → [保存]｜[不再提示此类]
用户可以一键关闭该类提示，也可以直接忽略。如果不点，不会自动落库。
3）特殊高价值场景：强制显式确认
什么时候才需要打断：用户明确说出 “记下来以后别的项目也要用” 这类强指令。此时才弹出确认，因为这是用户主动诉求，不会产生疲劳。
关键约束：无论置信度多高，高置信候选也不会自动写入可检索记忆库，只是存到隔离的临时候选池。
临时候选池有过期策略：例如 7 天未处理自动清理，避免无限堆积。
应对你提出的两种失效情况
用户疲劳机械跳过：因为没有强制弹窗，不需要每一条都点跳过，直接完全无视侧边候选池即可，不会产生机械操作；需要沉淀的时候再回头批量处理。
用户疲劳机械确认：因为高置信不会自动弹出确认按钮，不存在无脑点保存把垃圾灌入记忆库。
边界风险
trade‑off：把确认后置到侧边，会带来新问题：很多候选用户永远不会去审阅，有用经验丢失。
这是有意取舍：
开发助手记忆系统有两类失败：①记忆污染（存了大量垃圾，检索出来误导用户，危害极高）；②知识遗漏（部分经验没存进去，危害较低，可以用户事后手动补录）。
优先规避高危害的记忆污染。遗漏可以接受，污染不可接受。
补充备选增强机制：复用触发式反向确认。
哪怕候选一直没被用户审阅，当系统未来会话里识别到再次遇到相似场景，此时才把旧候选拿出来提示用户：“我们之前遇到过相似问题，是否把这条沉淀为项目记忆？”。
把确认时机从 “问题刚解决” 推迟到 “再次遇到”。知识真正第二次出现的时候，才是用户感知价值最高的时候。
问题 2：默认存入项目级；升级全局（跨项目记忆）靠什么信号
原始规则：项目记忆自动进入（经过上面确认流程）；全局跨项目记忆，绝不自动升级，必须有触发信号。
有两类信号，用户主动指令为第一优先级；系统观测复用成功作为第二级的提示信号，系统无权自动升级。
信号 A：用户显式主动指令（最高优先级）
直接指令例子：
“把这条升级为全局记忆，以后别的项目也用”
“这个经验是通用的，不限于本项目”
用户主动下达，则直接从项目记忆拷贝 / 迁移到全局记忆库。
信号 B：系统观测到跨项目复用成功，仅做提示，绝不自动升级
系统可以采集两类可观测信号，作为升级建议的触发条件：
跨项目场景命中信号
同一条项目级卡片，在不同项目上下文中，被检索召回，并且本轮用户实际采纳了该卡片给出的方案（从对话行为判断：问题解决，没有反驳方案，没有说这个方案不适用）。
注意：同一个项目内多次复用不算；必须是切换到另一个项目，复用成功，才说明它具备跨项目通用性。
多项目重复踩同类坑信号
系统观察到：不同项目里，用户反复遇到同类模式问题，在多个项目分别沉淀了高度相似的多张项目级经验卡片。
当满足上述信号，系统弹出建议提示，不是自动操作：
“这条经验已经在多个项目中生效使用，是否升级为全局跨项目记忆？【升级｜暂不｜永远不要提示这条】”
重要约束（防止系统乱升级）
仅仅 “检索命中” 不算，必须要复用成功。召回了但是用户否定方案，不能触发升级提示。
系统永远不能自动把项目记忆提升为全局记忆。只允许生成建议。
用户可以选择 “永远不要提示升级这条卡片”，消除后续打扰。
反例：哪些信号不能作为升级依据
卡片本身写得很像通用方案：AI 自我判断通用性是不可靠的，很多看起来通用的方案，暗藏本项目业务假设。
在同一个项目多次复用：只代表项目内有用，不代表跨项目通用。
高置信度候选：高置信只代表适合本项目，不等于跨项目通用。
存储实现细节
项目记忆升级全局，不做移动，做拷贝。
原始卡片依旧保留在原项目记忆库；全局库生成独立副本。
好处：
原项目知识库完整性不受破坏；
全局副本后续可以独立修改、标记版本，不会反向污染旧项目；
全局卡片可以标记来源：源自 XX 项目的项目记忆卡片。
边缘 case：一开始就是通用知识
用户刚解决一个问题，直接就说别的项目也要用。此时不走 “先存项目再升级” 流程，直接写入全局记忆。
总结关键设计要点浓缩
解决确认疲劳：置信度分级 + 差异化确认强度；高置信走隔离临时候选池，非阻塞 UI，不强制弹窗；只有用户主动诉求才打断对话。同时支持延后确认：第二次遇到同类问题的时候再提示沉淀。
升级全局记忆：没有全自动升级。两个来源：①用户直接指令；②跨项目复用成功，系统给出建议提示，用户确认后拷贝副本进入全局库。
风险排序：记忆污染 > 知识遗漏。宁可漏掉一些值得沉淀的知识，也不要自动把不确定的信息升入长期记忆。
