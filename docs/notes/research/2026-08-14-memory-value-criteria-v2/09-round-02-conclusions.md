 ## 一、分歧 A（价值公式因子构成）——已收敛
 
 round-02 中 ChatGPT / Claude / Grok 三个给出公式的平台在交叉比较后**独立收敛**：
 
 ### 收敛点 1：三种切法高度同构，分歧在「抽象定义 vs 工程分解」
 
 | 平台 | 对三种公式的裁决 |
 |------|----------------|
 | ChatGPT | 高度同构、非本质冲突：P(future use)×Benefit×Cost_forget 是「未来效用」的抽象定义；复用期望×稳定性×修正代价、跨情境价值×检索成本是把它拆成更可工程化的 observable factors |
 | Grok | 不同切法是同一决策问题的不同分解；裁决标准是「哪组因子最能直接指导实际筛选」，而非形式完备性 |
 | Claude | （未直接裁决公式，但承认自身方案缺口，见分歧 B） |
 
 ### 收敛点 2：统一公式形态——「期望净价值 = 乘性因子 − 减性成本」
 
 | 平台 | 收敛后的公式 |
 |------|-------------|
 | ChatGPT（主动修正上一轮） | EV(m)=P_use×P_valid×Impact − Cost_retain − Cost_forget；**放弃纯乘法**，Cost 降级为决策阈值/修正项 |
 | Grok | 期望净价值 ≈ P(future use)×Benefit×Stability − (检索/应用成本 + 预期修正代价) |
 
 两平台最终公式**结构一致**：`乘性价值因子 − 维护/遗忘成本`。分歧只在：Stability 作为乘性因子（Grok）还是作为 metadata/生命周期属性（ChatGPT）——后者认为 Stability 可被吸收进 P(valid|use)，前者认为应显式建模以便做过期降权。
 
 ### 收敛点 3：反对伪精确分数，主张离散等级 + 复用反馈校准
 
 - ChatGPT：不要 future_use=0.73 这种 LLM 伪精确；第一版用离散等级（rare/possible/likely/frequent × negligible/useful/important/critical），通过规则 + 统计逐步校准；「预测复用场景（reuse contexts）」而非「预测概率」——让系统从真实复用结果反学。
 - Grok：实践中不必追求精确数值打分；筛选时同时检查几个维度，允许用户对「稳定性」「修正代价」人工校准；单一乘积公式易产生虚假精确感。
 - Claude：维度二（风险信号）靠内容结构检测而非数值打分（见分歧 B）。
 
 ### 收敛点 4：最难拿数值的是 P(future use)——用「复用场景预测」代替
 
 ChatGPT 明确：P(future use) 是最难、最核心的难点（不可直接观察未来、distribution shift 大）；建议不预测概率而预测 `potential reuse contexts`，未来任务匹配时在线学习。这直接呼应了用户此前「召回后没有回收『命中率』渠道」的担忧——**检索命中/采纳反馈是校准 P 的唯一可靠数据源**。
 
 **结论 A**：分歧 A 收敛。公式方向 = `ReuseOpportunity × FutureValidity × Impact − RecoveryCost − MemoryCost`（ChatGPT 最终版），工程落地用离散等级而非连续分数；P(future use) 用「复用场景 + 行为反馈」校准。
 
 ## 二、分歧 B（触发时机：信号驱动 vs 任务节点结束）——已收敛
 
 ### 收敛点：两平台独立给出同一答案——「两级捕获」，且节点提炼是信号体系的一部分而非竞争者
 
 | 平台 | 立场 |
 |------|------|
 | Claude | 信号驱动确实有**结构性盲区**（第一次出现的坑、说一次就该记住的高风险内容）；但任务节点不是与信号驱动竞争的独立触发器，而是「过程信号唯一可见的时间点」——必须等工作单元闭合（问题→多次尝试→解决）才能识别过程信号；两者是**接力关系**（节点整理第一步先查重、只处理信号驱动没抓到的部分） |
 | Gemini | 完全需要两级：L1 Flash Cache（极低开销、无感知的 append-only 暂存，启发式/轻量模型提取 KV/Tag）+ L2 Periodic Refiner（节点批量整理：GC 丢弃无效尝试、增量提炼升维到规则）；引用 MemGPT 的 FIFO Queue 与 Archival Memory 模式 |
 
 ### 分歧 B 的附加收敛：Claude 主动修正「默认不记」原则
 
 Claude 承认「修正代价不对称」与「默认不记」存在真实张力，给出调和方案：**信号从一维变两维**——
 
 | 维度 | 管什么 | 门槛 |
 |------|--------|------|
 | 维度一：复用信号 | 未来会不会被用到（显式/纠正/重复） | 原有阈值 |
 | 维度二：风险信号 | 一旦遗忘/记错后果多严重（祈使禁止、不可逆操作、安全/权限关键词） | **更低门槛，独立生效** |
 
 高风险内容即使只出现一次也应立即捕获，但标记「待确认」状态，通过追问用户或后续行为验证提升确信度——**不是一次性当板上钉钉**。这正好呼应了用户此前讨论的「安全门」问题（记了反而有害）。
 
 ### doubao 的确认闸门设计（分歧 B 的交互侧）
 
 doubao 补充确认疲劳的解法：候选置信度分级 + 差异化确认强度——
 
 | 置信度 | 信号 | 确认方式 |
 |--------|------|---------|
 | 高 | 会话闭环+模式化+低噪声+无强项目绑定 | 静默候选池（非阻塞侧边栏批量审阅，7 天过期），不强制弹窗 |
 | 中 | 版本边界模糊/绑定项目业务 | 轻量行内提示，可一键忽略 |
 | 低 | 单次实例/未验证/发散闲聊 | 直接丢弃，不进候选池 |
 | 特殊 | 用户显式「记下来以后也要用」 | 才强制弹窗确认 |
 
 并补充「复用触发式反向确认」：候选未审阅时，未来再次遇到相似场景才提示沉淀（第二次出现才是用户感知价值最高的时机）。
 
 **结论 B**：分歧 B 收敛。触发 = `两级捕获`：L1 轻量随时记录（信号驱动 + 高风险内容低门槛捕获，标「待确认」）+ L2 节点批量提炼（commit/PR/修 bug 后，先查重再补抓过程信号 + 冲突检测 + 归档分层）。确认交互按置信度分级，非阻塞优先。
 
 ## 三、分歧 C（留存形态：统一 vs 分流）——方向收敛，物理形态待项目内验证
 
 | 平台 | 立场 | 理由 |
 |------|------|------|
 | Grok | **统一为「Knowledge Card + 类型 schema」**：核心实体只有一种（公共字段），type 标签（可多选）绑定扩展 schema（ADR 需 Context/Decision/Consequences；失败模式需 Trigger/RootCause/Mitigation/Verification）；检索/生命周期/权限统一实现，UI 按类型动态切换 | 避免跨库检索与维护摩擦；一张卡片可多标签；物理拆分只在极端安全场景才考虑 |
 | Gemini | **本质是三种不同实体**，物理上应分化存储：声明式规则（语义记忆，全量静态注入 system prompt）、架构意图图谱（关系记忆，图检索/关联扩展）、程序化 SOP（程序记忆，动态工具调用）；强行统一会损失（规则检索失效、图谱关系断裂、SOP 失去可执行性） | 三种形态认知本质不同（Semantic/Relational/Procedural），检索/注入方式不同 |
 
 **方向收敛**：两平台都同意「统一捕获层」（Gemini 的 L1/L2 也适用于 Grok 的卡片）；分歧仅在**物理存储形态**。而这一点**无法由平台回答裁决，必须回项目内验证**——看本项目 `schema.sql` / `src/models/` 现有实体设计支持哪种形态，以及是否已有类型标签机制（README 里提到 container_tag = {keyId}_project-<dir> 等）。
