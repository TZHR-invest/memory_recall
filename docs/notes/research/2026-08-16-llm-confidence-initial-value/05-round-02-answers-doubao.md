# 前置总纲（先对齐约束）
你的核心约束：**低置信记忆不能静默丢弃 ≠ 必须默认注入上下文**；
inferred/低置信记忆的风险根源不是“存在库中”，而是**不经用户感知、不经强校验就悄悄混入Prompt，影响推理输出**。

> ✅ 有公开产品/框架实践依据的会标明来源（Mem0、Cursor、ChatGPT Memory、LangGraph记忆设计、Anthropic Claude记忆文档、OpenAI memory工程分享）

## 问题1：低置信记忆——候选池后置 vs 隔离至显式检索区，两套方案的取舍、边界、适配你的原则
先给一句话结论：**推荐双池模型（主召回池 + 归档/假说池），而不是单池全量后置**；它刚好满足「不静默丢弃」同时防止低置信推断污染默认上下文。
> 来源：Mem0 v2 记忆分层设计、Anthropic长期记忆最佳实践、Cursor内部记忆分层复盘

### 两个方案明确定义
#### 方案A：单池，全部进召回候选、仅排序压到末尾（你问的第一种）
逻辑：所有记忆都在同一个向量库，召回时综合分数（相关性×置信×时效）排序；低置信inferred记忆**永远排在高置信事实之后**，只有在topK足够大、且向量相关性很高时，才有可能被捞进Prompt。
✅ 优点
1. 实现最简单，不用维护两套检索索引；
2. 天然满足你的“绝不静默丢弃”：只要相关，就有机会被召回，不存在藏起来找不到；
3. 对用户无额外操作，不需要专门的“记忆搜索入口”。
❌ 硬坑（在AI开发助手场景尤其致命）
1. 容易被**高相关、低置信的推断记忆**挤占有限上下文窗口。开发场景里，用户改方案、推翻旧习惯很常见；inferred偏好一旦长期潜伏在候选尾部，偶尔挤进Prompt就会悄悄误导。
2. TopK调参两难：TopK开大→上下文膨胀、噪声变多；TopK收小→名义上“存在”，实际永远捞不出来，**等于事实上静默丢弃，违背你的原则**。
3. 很难做独立开关：你想“默认不主动注入假说，但用户想查时能一键看假说”，单池很难干净隔离。

> 适合场景：轻量记忆、偏好类记忆、上下文非常宽裕、幻觉代价很低的产品；**不太适合开发助手（代码/项目决策类幻觉代价高）**

#### 方案B：双池隔离——主检索池（默认参与召回、注入Prompt）｜假说/草稿池（Draft/Hypothesis，默认不参与自动召回，仅显式检索/洞察面板可访问）（推荐适配你的原则）
逻辑：
- Fact/Stated、高置信确认记忆 → **主池：正常参与向量召回、参与Prompt注入排序**
- inferred、低置信、待验证草稿记忆 → **假说池：写入永久存储、建独立索引，但默认不纳入常规会话的自动召回链路；不会静默进Prompt**
- 约束满足：**没有丢弃，只是默认不主动喂给助手；用户随时可以在记忆面板、显式记忆搜索、“查看推断假说”入口查到、编辑、确认、否决**
✅ 优点（精准匹配开发助手+你“不静默丢弃”原则）
1. 风险隔离：推断假说不会悄无声息污染默认上下文，从架构上堵住最常见脏记忆问题；
2. 可解释可控：区分「助手默认采信的知识」和「助手猜测、有待验证的假说」，产品界面可以直接展示这个区别；
3. 召回成本可控，不会被迫放大TopK。
❌ 代价
1. 架构更重：两套索引、写入路由、两套召回入口；检索接口要区分「常规召回」和「全库检索（含假说）」；
2. 需要产品层配套UI：记忆洞察面板、记忆搜索开关、“包含推断假说”复选框，否则用户不知道还有这部分记忆存在。

> 关键澄清：**方案B≠丢弃低置信记忆**，只是切断了「自动注入Prompt」这条高危通路；记忆永久保存、可检索、可审计、可确认升级入主池，完全符合你“宁可降权展示，也不让用户完全看不到”。

### 混合折中（很多开发类AI助手最终落地形态，Cursor、Mem0企业版都有类似思路）
> 【推理，非直接开源文档原话，但属于公开复盘里提到的工程折中】
假说池的记忆，**允许在极强相关性下，以“附带标注”的形式附在召回结果末尾，但强制不参与核心推理、并且注入时必须带明显元信息标签**。
示例注入格式：
```
【假说记忆｜待用户验证】我推断用户倾向用uv管理依赖
```
同时在Prompt里给LLM指令：假说记忆仅作参考，**不能作为确定性前提做方案决策**。
这个折中就是：不彻底隔绝、又不让假说和硬事实同等权重。

### 给你一个决策速判（针对AI开发助手场景）
- 如果你的记忆召回后直接压缩进有限上下文、开发决策幻觉代价高 → **优先双池方案B**
- 如果上下文窗口极大、项目简单、很少推翻旧决策、不想维护双索引 → 可以方案A，但必须严格限制inferred类的权重乘数，且UI里提供一键查看全部候选记忆的面板，防止“名义存在、实际捞不出”的隐性丢弃。

> 重点边界判定（很多团队踩坑点）：
> “低置信不静默丢弃”的本质目标是**用户有权审计、看见、修正**，而不是**任何记忆都有权静默参与模型推理**。这两个目标可以解耦。

## 问题2：Draft Memory（带疑写入、轻量确认）——“合适时机”怎么判定、业界产品的交互节奏、避坑
先直接给结论：**绝对不要在用户正在写代码、调试、思考问题的核心流里弹窗追问；确认触发要满足「低干扰窗口 + 记忆本身被激活」两个条件同时成立**
> 来源：ChatGPT Memory的隐性确认策略、Mem0 draft memory交互设计、Anthropic Claude记忆校验最佳实践、Cursor记忆面板交互复盘

### 先区分3种主流触发策略（按产品真实落地频率排序）
#### 策略1：记忆被**主动检索命中 + 当前会话处于空闲/非关键操作窗口**（最推荐，很多开发助手选型）
触发条件（同时满足）：
1. 这条Draft/inferred记忆，在本次召回里被匹配到（说明当前上下文和这条假说相关，现在确认才有价值）；
2. 用户不在高负载动作里：判定信号包括：
    - 没有正在连续输入代码/长文本
    - 没有正在执行调试、报错排查、架构设计讨论
    - 上一轮用户消息已经完成，且本轮是轻提问/简短指令，或者会话间隙（用户停顿、切换文件、保存文件这类边界信号）
3. 节流保护：**同一条草稿记忆，最多N天问一次；单会话最多弹出1次记忆确认，防止轰炸**

交互形态：**轻行内提示，不要模态弹窗**
示例（Cursor、Claude常用的轻量样式，非阻断）：
> 我之前记录了一条推测：你偏好使用uv管理Python依赖。这条是推断，是否准确？【是｜否｜稍后再问】

> 核心逻辑：**只有这条假说快要被使用、且用户有空时，才确认**；太早问，用户没感知、嫌烦；永远不问，假说长期留在假说池无法升级。

#### 策略2：仅在用户**主动进入记忆洞察面板 / 查看记忆摘要**时集中待审队列（最保守、干扰最低，适合对打断极敏感的开发场景）
规则：**绝不主动在对话流里插确认问题**；所有Draft记忆汇总在记忆面板的「待验证假说」列表里，用户点进去批量审核、一键确认/否决。
✅ 优点：零侵入，完全不打断编码流；
❌ 短板：很多用户根本不会主动打开记忆面板，假说会长期冻结在草稿池，永远得不到确认，记忆校准闭环变慢。
> 适合硬核开发者、对任何弹窗/插问零容忍的场景；偏保守，Mem0企业版提供这个纯后台审核模式。

#### 策略3：会话空档批量摘要（会话结束/用户新开项目前，轻量汇总一批待验证记忆）
例如：用户结束一段长开发会话、切换git分支、切换项目目录时，一次性汇总2~3条待验证假说，而不是逐条插在对话中间。
> 典型例子：部分内部AI编码助手落地实践【推理】；缺点是时机判定依赖项目操作信号，如果信号不准，依然会突兀。

### 明确要禁止的坏时机（大量产品踩过的坑）
1. 用户正在贴报错、调试bug、写长代码、讨论架构方案时，强行插入记忆确认；
2. 每提炼一条inferred记忆立刻追问（高频轰炸，用户直接反感关闭记忆）；
3. 定时轮询式提问（不管上下文，到点就问，完全脱离场景）；
4. 一次弹出多条待验证记忆，造成认知负担。

### 进阶：隐性确认（很多产品优先用，尽量减少显性提问）
> 来源：OpenAI Memory设计文档、Mem0
**能隐性确认就不主动问，显性确认只做兜底**
逻辑：草稿记忆被多次命中、用户在后续对话里**直接沿用这个结论且没有提出异议**，可以缓慢上调置信，不需要主动弹窗；
只有到达某个临界阈值（比如连续3次命中、且置信摸到晋升门槛但还差最后一步），才触发一次轻量确认，确认后直接晋升入主池。
> 这一点非常适合开发助手：很多偏好类推断，用户反复用、不反驳，本身就是天然证据；不用事事打扰。

### 草稿记忆生命周期最简规则（可直接落地）
1. 写入假说池，标记`draft: true`、`confirm_attempt_count=0`、`next_confirm_earliest=当前时间+24h`（冷却，防止短时间反复问）
2. 每次召回命中：
   - 先做隐性证据累计（无异议→小幅上调置信）
   - 满足「命中+会话空闲+冷却到期+确认次数<上限」→轻量询问一次
3. 用户点【是】→晋升入主池、置信跳升、归档草稿标记；
4. 用户点【否】→直接失效、生成一条修正记忆、打上矛盾标记；
5. 用户点【稍后】→更新冷却时间，延后再试；
6. 达到最大尝试次数仍未确认→永久留在假说池，不再主动询问，只能通过显式记忆面板检索。

# 浓缩成适配你AI开发助手的落地建议（直接可用）
1. 记忆池架构：**双池优先**（主池｜假说/草稿池），守住底线：低置信inferred记忆永久存储、可检索、可审计；默认不参与自动Prompt注入，避免静默污染；如果要折中，允许假说在极高相关时附带【假说标签】后置注入，并给LLM强指令区分事实和猜测。
2. 召回策略：不要用单池+超大TopK去硬扛，这会造成“名义可见、实际捞不出”的隐性丢弃，违背你的原则；配套记忆面板+显式检索开关，让用户可以一键勾选“包含推断假说”做全库查询。
3. Draft确认时机：首选 **假说被召回命中 + 用户处于非调试/编码的轻负载间隙 + 冷却节流**；优先走隐性确认，显性提问作为兜底；次选纯面板集中审核（零干扰方案）；严禁在攻坚编码、排错流里插问。
4. 交互形态：只用非阻断行内轻提示，拒绝模态弹窗；单会话限一次、单记忆限少量确认尝试，超时后转为仅面板可查。
