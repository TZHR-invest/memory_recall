先说一个前提性区分

自陈信号有两种失效方向，得分开处理，因为它们的偏差性质、可校准方式、该给的权重都不一样：

假阳性(false uptake):模型说"用了 X"，但其实没真正依赖 X(可能是复述了自己本来就知道的东西,恰好和 X 内容重合)。这是 Q1/Q2 要防的。
假阴性(missed uptake / 隐性使用):模型真用了 X 影响了推理,但没有写进 ref。这是 Q3 要补的。

这两者在 RAG 可信度研究里被称为 unfaithfulness(模型忽略/不依赖给定上下文却仍答对,常常是因为答案本来就在参数知识里)——已知这个"context 和 parametric knowledge 的拉锯"是普遍现象,不是你们系统特有的毛病,只是没人给出过便宜的根治方案。

1. 如何校准、估计噪声率

最干净的 ground truth 来源是反事实消融(counterfactual / leave-one-out):把模型声称用到的那条记忆从上下文里拿掉,重新生成一次,比较两次输出的差异。如果去掉后输出几乎不变,说明这条记忆大概率不是因果必要的,是假阳性候选。这条思路在 RAG 归因研究里有直接对应(ContextCite、AttriBoT 的"近似省钱版 leave-one-out"、RAGONITE 的 counterfactual attribution),核心结论都指向同一点:基于相似度/自陈的归因只是"看起来合理",基于消融的归因才是"因果的",两者经常对不上。

工程化落地建议:

不要全量做,leave-one-out 要多一次(或者半次,AttriBoT 那类近似方法可以省)推理调用,成本不低。只在一个小比例抽样(比如 1%~5% 的"自陈使用"案例)上做,把它当作校准集,不是线上实时机制。
用这个校准集算一个混淆矩阵:模型自陈"用了" vs 消融后确认"真用了",得到假阳性率 P(自陈=用 | 真实=没用);模型自陈"没用" vs 消融后发现"其实变了"，得到假阴性率(对应 Q3)。这两个数字不是一次性的,应该按记忆类型/任务类型分层估计——我猜测(没有依据,是推测)代码类的"硬事实"记忆(某个坑的修复方法)自陈准确率会明显高于"软偏好"类记忆(代码风格倾向),因为前者要么用了要么没用,判断边界清楚,后者容易被模型"顺嘴认领"。
更便宜的辅助校验(不做消融,只做文本层面比对):用一个便宜模型检查"回复里的具体断言是否真的能在这条记忆文本里找到对应"。这个比消融便宜得多,但精度更低——它能抓住"我说用了但回复内容跟这条记忆根本不沾边"这种粗糙假阳性,抓不住"内容对得上,但其实模型不靠这条记忆也会这么答"这种精细假阳性。建议两层组合:全量用便宜的文本比对做粗筛,小比例抽样用消融做精校,拿精校结果去估计粗筛方法本身的系统性偏差,再用这个偏差去修正全量粗筛的分数——这是我自己的工程建议,不是照搬某篇文献。
一个几乎零成本的 sanity check:直接切历史日志,对比"自陈用了 X"和"自陈没用 X"两组样本,看它们后续的结果分布(代码采纳率、坑复现率)有没有显著差异。如果没有,说明自陈信号本身信息量就不够,值得警惕,但这只能告诉你"有没有用",不能单独告诉你噪声率具体多大。
2. 权重应该压多低

我的核心建议是:自陈信号不应该单独触发任何"提权"决策,只能作为候选筛选/曝光计数,真正让置信度上调的必须是至少一个独立的、结果层面的信号(没有被重复陈述、没有被纠正、代码被采纳、坑没复现)。理由不只是"精度不够",而是它的偏差是系统性、单方向、会自我强化的——一条记忆如果内容碰巧和模型的参数知识重合,模型会持续"自陈用了"，如果这个自陈直接喂回权重,就会形成一个纯粹的confirmation loop:记忆从没被真正验证过,却因为反复被"声称有用"而越滚越可信。这是三种反馈信号里唯一一种有明确正反馈闭环风险的,必须单独限权,不能和"结果确认过的正反馈"用同一套线性累加逻辑。

具体到数字(这是我给的经验性建议,不是文献结论,需要用你们自己校准集的噪声率去调):

把"有结果确认的正反馈"定为基准权重 1。
"自陈使用但无其他确认"给一个明显小一个数量级的增量(比如 0.05~0.1),而且要设上限——纯靠自陈信号能把一条记忆推到的置信度天花板,要显著低于结果反馈能达到的天花板,防止它靠"量"堆出虚假的高分。
反过来,"自陈没用"可以给相对更高的可信度,因为模型没有明显动机去主动否认一条它其实用了的记忆,假阴性率大概率比假阳性率低。但这个信号不该直接用来删记忆,更适合拿去调整检索侧的匹配范围(这条记忆总是被召回却总说没用上,可能是召回策略太松,不是记忆本身有问题)。
3. 隐性使用怎么补

诚实说:条目级别的完全覆盖做不到,不用硬追。但有几个性价比不同的补救层次:

源头降低隐性使用比例:把引用门槛做低一点——除了正文强引用,再加一个轻量的"touched_memory_ids"字段,标准是"哪怕只是背景性地参考过也报",鼓励宁可多报不要漏报。这只是缓解,治标不治本,模型可能真的没意识到自己用了。
如果能拿到模型内部信号(自部署开源模型才行,套壳商用 API 基本走不通):读生成过程对记忆文本片段的 attention/贡献度,筛出"高关注但没被自陈引用"的记忆作为隐性使用候选。但要注意 attention 高只说明模型"看过"，不说明"结果依赖它"——这是相关性证据不是因果证据,只能当线索,不能当结论。
小比例抽样 leave-one-out,专门盯"自陈没用"的案例:对模型自陈"完全没用到任何记忆/只用了 A 没提 B"的案例做少量抽样,把 B 也拿掉重新生成,看输出是否变化。这个方法的好处是不依赖模型自己诚实与否,是外部可验证的,和 Q1 用的是同一套工具,只是抽样目标从"验证假阳性"换成"验证假阴性"。成本可控,建议长期作为一个固定比例的后台校准任务跑,而不是一次性项目。
接受个体丢失,退到统计层面补偿:不追求每条记忆的隐性使用都被抓到,转而追求"这一类记忆(某主题/某种写法)的隐性使用率总体上偏高还是偏低"。做法是故意对一小部分同类记忆做随机屏蔽(类似 bandit 的 explore),对比屏蔽组和非屏蔽组下游结果的差异,把"记忆是否有用"从一个只能被动观测的问题,变成一个可以主动做实验的问题。这个成本最高、也最"重"(要牺牲一部分线上体验做探索),我的建议是只有当记忆库规模足够大、样本量足够多时再上,产品早期没必要做,前面三条已经够用。

综合来看,我认为合理的资源分配是:第 1 条(格式引导)几乎零成本先做上;第 3 条(小比例 leave-one-out 双向校准)是性价比最高的核心机制,建议作为长期后台任务;第 2 条看你们的模型部署方式决定能不能做;第 4 条留到规模上来之后再考虑,不是第一版该碰的东西。
