# 04 · round-02 追问（交叉轮：收敛三大分歧）

> 执行方: codex 操作浏览器 · 方式: 在各平台 **round-01 同一会话**内继续追问（保持上下文），回答原文回填
> 依据: [08-round-01-conclusions.md](08-round-01-conclusions.md) 第三节「关键分歧点」

## 本轮目标

round-01 五平台在**无预设**下高度收敛（归因问题 + 多信号融合 + 开发结果痕迹 + 负反馈优先 + 生命周期），
但留下三个分歧点。round-02 只针对这些分歧向相关平台追问，**不增加平台、不引入新问题**：

| 分歧 | 发问平台 | 问什么 |
|------|---------|--------|
| A. 归因粒度（单条记忆级 vs 记忆组级） | ChatGPT / Gemini / doubao | 单条事件链的兜底；巩固/归档的粒度；组级范式的成立条件与组内坏记忆防护 |
| B. 模型自陈信号（ref 标记/使用标注）的可信度 | Claude | 自陈偏差怎么校准；第一版权重该多低 |
| C. 负反馈与归因陷阱的落地防护 | ChatGPT / Grok | 状态机转移阈值与检索策略区分；错误负反馈的防护与恢复路径 |

## 追问文本（按平台打包，整块复制；不点名其他平台，只针对该平台自己回答里的薄弱点/冲突点）

### ChatGPT（分歧 C + 分歧 A）

```text
上一轮你设计了 useful/irrelevant/stale/wrong/harmful 的五状态机，并强调"不要因为一次没用就降低 memory，
必须做 Bayesian/evidence accumulation 式更新"。另外你还提出了两个学习器的区分（内容学习器 vs 检索策略学习器）。
落地时有三个具体问题想请教：

1. 状态转移的触发阈值怎么定？positive evidence 与 negative evidence 累积到什么比例/次数才允许从 Useful 迁到
   Stale 或 Harmful？证据稀疏的冷启动阶段怎么防误判？
2. "检索策略问题"和"记忆内容问题"怎么可操作地分开——一次召回没用上时，怎么判定该调整的是 retrieval policy
   而不是记忆本身？有没有不依赖人工的判定规则？
3. 你建议 V1 就建"Memory Event Schema"（retrieved / mentioned / used_in_plan / linked_actions / task_success），
   事件是单条记忆粒度。但实际使用里往往是整组记忆一起注入、一起影响输出——单条粒度的事件链在这种场景下
   归因可靠性会不会崩？要不要在事件里加"组"这一层？
```

### Claude（分歧 B）

```text
你上一轮建议"让主模型在生成时显式声明用到了记忆 ID X/Y"，作为最便宜直接的 uptake 信号采集方式，
同时你自己也指出了模型自陈的偏差（"没真正起作用但模型觉得自己用了"）。想请你把这个信号的可信度工程化：

1. 自陈偏差具体怎么控制/校准？有哪些低成本的交叉验证手段，能估计"自陈用了但实际没用"的噪声率？
2. 如果自陈只作一阶近似，第一版应该把它的权重放多低，才不至于让"会自我合理化的模型"反向强化错误记忆？
3. "隐性使用"（看到了、影响了推理，但没写 ref）这部分怎么补——是接受丢失，还是有别的低成本的隐式信号能覆盖？
```

### Grok（分歧 C）

```text
你上一轮特别警告："错误的负反馈可能加速遗忘有用但低频的记忆；过度强化可能固化过时模式"，
并主张保守衰减 + 人工可审计接口。想请你把这个防护具体化：

1. "低频但有用"的记忆和"过时但还没被揭穿"的记忆，在信号上怎么区分？什么信号能分辨这两者？
2. 保守衰减的具体机制怎么设计（衰减速率、触发条件、恢复路径）？
3. 人工可审计接口应该暴露什么，才能在误判发生时快速纠偏而不需要重训任何模型？
```

### Gemini（分歧 A）

```text
你上一轮建议异步冲突检测：捕捉到用户纠错信号（"我们改用 X 了"）时触发检索，把旧记忆标记为 Superseded。
这个机制有两个工程细节想请教：

1. 用户纠错信号和旧记忆的"冲突"怎么判定才可靠？用户的一句话可能同时推翻多条旧记忆，也可能只是局部修正
   （比如只有版本号变了，其余仍成立），误判成本有多高、怎么设触发阈值？
2. 归档/合并/提炼（把多条零碎记忆合成更高维度的"工程准则"）是在单条记忆粒度做，还是按主题/项目分组做？
   不同粒度的取舍是什么？
```

### doubao（分歧 A）

```text
你上一轮在"额外思考"里提出了一条不同的路线：把记忆按主题/项目/版本分组，整组开关、对"记忆组"给反馈，
而不是对单条细碎记忆做归因。想请你把这个方案再推演一步：

1. 什么条件下值得从"单条归因"升级到"组级管理"？组级会不会掩盖组内坏记忆（一条有毒记忆搭了同组好记忆的便车）？
2. 分组的粒度怎么定（项目/主题/版本）？跨组共享的记忆（比如"团队编码约定"）怎么处理？
3. 落地时，组级反馈和单条统计是二选一，还是两层共存（组级粗调 + 组内单条细调）？
```
