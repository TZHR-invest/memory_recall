## 一、问题陈述

外部调研定案的原子判据是：**粒度 = 独立生命周期（两个部分未来可能被分别裁决 → 拆）**，
配套"整篇文档是证据不是结论"（原文照抄 = 分层错误）。

但用户指出一个调研未覆盖的盲区：**文档类 Evidence 与对话类 Evidence 的本质差异**。
对话（"我们这期先用 Miniflux，最多 20 个源"）适合逐句拆条成原子 claim——每句都是一个
可独立证伪的决策。但文档（"LensDiary Core Architecture Patterns"）不一样：

- 文档是**人写的、结构化的、有版本的历史产物**，它本身已经是"精炼过的知识"；
- 对文档做"逐句拆分"是**把成品重新打回原料再加工**——低价值、易失真、且丢失文档的整体性；
- 文档的正确处理应该是**概括**（这篇文档讲什么、定位于哪、路径在哪），而不是**细拆**
  （文档里每句话是什么）。

用户进一步指出关键约束：**add 进来的文档必须带"文档路径"这个元数据，否则无法合理使用**。
现实库验证了这个担忧是真实的（见 §三）。

## 二、先对齐：我们讨论的"文档"指什么

| 形态 | 例子 | 归属 |
|------|------|------|
| **对话中的陈述**（用户口头说的决策/事实/偏好） | "我们这期先用 Miniflux，最多 20 个源" | 对话类，逐句拆条 ✅ |
| **文档内容被整体塞进来**（长文本，结构化标题） | "LensDiary Core Architecture" 2383 字原文 | 文档类，本文讨论对象 |
| **指向文档的断言**（"正式规划文档是 PROJECT_PLAN.md"） | foundation 拍板例子 | 元断言，已是原子 claim ✅（不拆） |

讨论边界：**本文只谈"文档内容被整体塞进来"这一类**——即现实库里那批
"# LensDiary ..." 标题开头的长 evidence（2383/1722/1657/1333 字等，共 10+ 条，全部来自迁移）。

## 四、为什么文档的"逐句拆分"是错误方向（引用调研）

外部调研（[99-final-conclusions](research/2026-08-19-claim-atomicity/99-final-conclusions.md)）给出了
三个直接支撑"文档应概括而非细拆"的论点：

**1. 文档照抄是"分层错误"，不是"粒度错误"（C2，全平台一致）**
平台原话：2383 字整篇文档被原样塞进一条结论，"**这不是'一条结论太粗'，而是'零条结论、
一份证据被误标成了结论'**"。推论：**文档本来就该留在 Evidence 层**——那么文档在 Evidence 层
的"正确用法"是什么？调研说"从文档中提炼真正可证伪的判断"（如"该架构后端用 Python+FastAPI"）。
但这里要追问：**从一篇文档提炼 N 条"事实断言"，与从对话提炼 N 条"决策断言"，价值一样吗？**
对话里的决策是用户当场做出的、会话独有的、不落文档的——提炼才有增量价值；
文档里的内容**已经写在文档里、且文档就在仓库里**——提炼成 claim 是"复制"而非"理解"，
且复制会过时（文档更新了，claim 还挂着旧结论）。**这正是用户直觉的深层原因：对文档做
逐句拆条 = 把"可重算的派生结论"建立在"会漂移的静态快照"上，方向反了。**

**2. 自足性/上下文张力（C1 引用 TriQua）**
调研承认"原子性与上下文保留有张力，必要上下文要用 qualifiers 保留"。文档的"上下文"是
**整篇的结构**（章节关系、前言、设计取舍的理由）——逐句拆条恰好是拆文档最伤上下文的方式。
文档拆成 30 条平行断言后，你无法回答"这个项目架构上为什么这么设计"——那个答案在
文档的**叙述结构**里，不在任何单句里。

**3. learned-pattern 的教训（C5，Gemini/Grok 一致）**
调研对 learned-pattern 类明确：**"条件–做法–结果"的因果链不能拆碎，拆碎丢工程价值**。
文档是更大规模的"条件–做法–结果"复合体——架构文档的"为什么"横跨多个章节，
比单条踩坑经验更不可拆。

**综合**：调研的原子判据（独立生命周期）**对对话类证据成立，对文档类证据不适用**
——文档的内容不会"被用户单独纠正其中一句"（用户纠正的是文档本身，走文档版本，不是走 claim），
文档的事实不依赖 claim 的可裁决性（文档自己就是裁决对象）。

## 五、文档的正确处理：概括 + 路径（用户提案，展开）

用户提案（我认同并展开）：

> **文档类 evidence 的提炼逻辑 = 概括文档内容和路径，而不是逐句细拆。**

具体化：

| 项 | 内容 |
|----|------|
| **claim 形态** | 一条（或极少几条）**概括性 claim**："`<scope>` 项目的 `docs/<path>` 定义了 `<主题>`（架构/API/配置……），核心要点：……" |
| **claim_kind** | fact（文档定位事实），不是被拆碎后的多个 fact |
| **元数据** | evidence 必须带 **file 路径**（`source_ref.file` / `source_ref.repo` / `source_ref.commit`），claim 引用它 |
| **不做什么** | 不逐句拆条；不从文档批量生成"文档里写了 X"式 claim（那是复制不是理解） |
| **失效方式** | 文档更新/删除 → 走证据链重算（文档路径是 key），不是逐条 supersede |

**为什么概括比细拆对？**

1. **文档的"可独立裁决单元"是文档本身，不是句子**：用户纠正文档 = 改文件 + 提交，
   不是在工作台逐句 confirm。所以原子判据的"独立纠正"测试对文档**指向文档整体**；
2. **概括 claim 是"指针 + 摘要"，不复制内容**：召回命中它 → 知道"有这个文档、讲什么、
   在哪" → 需要细节时按路径去读原文（相当于 Claude Code 的"索引行 + 按需加载"模式，
   调研 doubao 引用过）；这比把 2383 字复制进 claim 又省又不过时；
3. **路径是防过时的锚**：`file + commit` 让 claim 可以校验"文档还在不在、变没变"，
   文档被迁移/删除时能级联失效——无根文本做不到。

## 六、选项分析（2026-08-19 已定案：无路径文档 → 当长消息处理）

| 选项 | 做法 | 优点 | 代价 | 定案 |
|------|------|------|------|------|
| **A. 文档概括 + 路径** | document 类 evidence 必须带 file 路径；提炼=概括 claim（指针+摘要）；文档变更走重算 | 语义正确、防过时、召回即"文档在哪" | 需要采集端带 file 元数据（插件/迁移脚本改造） | **后置 P2**（跟文档采集一起，走指针式） |
| **B. 文档继续逐句拆条** | 把 2383 字也按原子判据拆成 N 条 fact | 与对话统一流程 | 复制文档内容、无整体性、必过时、成本高 | 否（对"有路径文档"）；但对"无路径长消息"等价于 C 的"长消息处理" |
| **C. 舍弃无路径文档** | 没有 file 路径的文档类 evidence 不建 claim | 最干净，不制造无根 claim | 丢失"文档存在"信息；碰 Evidence 不可再生（证据层不删） | 否（见 §四论证） |
| **D. 混合：有路径概括 / 无路径长消息** | 带 file 的文档 → 概括 claim（P2）；无 file 的长文本 → 当长消息拆条（一期） | 语义正确 + 不保留无根产物 + 不丢 agent add 的内容 | 需要区分两种来源；迁移数据需审计 | **✅ 定案** |

**定案：D（混合）。** 其中"无路径文档当长消息处理"的完整论证见 §四；"指针式 vs 摘要式"区别见 §六.1。

### 六.1 指针式 vs 摘要式（用户问"不懂区别"，解释）

| | 指针式（Pointer） | 摘要式（Summary） |
|---|---|---|
| **claim 长什么样** | "`docs/architecture.md` 定义了 LensDiary 架构，要点：管线/技术栈/配置" | "LensDiary 架构 = Python+FastAPI+SQLite，本地优先，11 阶段管线……" |
| **内容放哪** | 不复制细节，claim 是"文档存在 + 在哪 + 讲什么"的目录条目 | 把文档核心内容浓缩进 claim，像读书笔记 |
| **依赖** | **必须依赖路径**（没路径没法指） | 不依赖路径，脱离文档也能用 |
| **过时风险** | 低（细节不复制，原文变了 claim 只失去效锚） | 高（文档更新后，浓缩的 claim 还是旧内容） |
| **召回命中后** | 需要细节 → 按路径读原文（Claude Code"索引行 + 按需加载"模式） | 直接用 claim 内容，不读原文 |
| **存储** | 省（不复制全文） | 费（浓缩仍占空间） |

**一句话：指针式不复制内容（防过时、省存储、路径是锚）；摘要式复制/浓缩内容（脱离路径也能用，但会过时）。**
已定案走**指针式**（配合 P2 文档采集，到时有路径可指）。

## 四、为什么"无路径文档当长消息处理"可行（用户要求论证，2026-08-19）

> 论证目标：无路径文档（现实库那批 2383/1722/1657 字"# LensDiary ..."长文本）
> 不"舍弃"、不"概括"（无路径概括不了），而是**当长消息按对话类拆条逻辑处理**——可行且最优。

### 四.1 前提：什么让一段文本成为"文档"——是路径，不是内容长相

一段文本是不是"文档"，不由它长得像不像文档决定，而由**它有没有文档身份**决定。
文档身份 = 路径（file + repo + commit）：

- **有路径** → 有版本、可定位、可校验（能查"这个文件还在吗、变了吗"）、可随文档变更级联失效；
- **无路径** → 以上全无，它就是"一段被记录下来的文本"。

所以"无路径文档"是误导性说法：**没有路径，语义上就不是文档，只是一条内容长得像文档的长消息。**
当长消息处理不是降级，是正确定位。

### 四.2 当长消息处理 = 保留 evidence + 按对话类拆条

- 保留 evidence 全文（Evidence 不可再生，不删）；
- 从长文本按原子判据（独立生命周期）拆出有独立生命周期的原子 claim；
- 现实库那 10+ 条恰好全部是 `agent_add`（来自迁移）——本来就该走 agent 自报内容路径。

### 四.3 可行的四个理由

1. **符合原子判据**。2383 字里"后端 Python+FastAPI""SQLite+sqlite-vec""高德 API 逆地理编码"
   "fastapi>=0.109.0"这些内容，用户未来完全可能只改其中一个（换数据库/升依赖/换 API）——
   独立纠正测试通过，该拆。且这些内容是**当初 agent 手动 add 的**（意图 = 觉得值得记），
   拆条正是忠实执行"记住这些内容"。

2. **不违反"原文属证据层"**。调研反对的是"原文照抄进 claim"（分层错误）。拆条 ≠ 照抄——
   拆条是从长文本**提炼**原子断言（claim = 系统对证据的理解产物），原文留在 evidence。符合 foundation 定义。

3. **与"文档概括"不冲突，是分流不是矛盾**。两条路径并存：
   - 有路径文档 → 概括 + 指针（细节走原文，P2 做）；
   - 无路径长消息 → 拆条（没有原文可指，内容只能靠 claim 承载）。
   差别就在"有没有地方可指"——路径是分流开关。

4. **成本可控**。拆条 1 次 LLM 调用/条，个人规模可承受（调研 C7）；"宁可多拆"已定案
   （错误可恢复性不对称：拆细可合并不破坏 confirm 记录，拆粗破坏裁决历史）。

### 四.4 为什么优于"舍弃"

舍弃丢的是 agent 手动 add 的内容（意图被浪费），还碰 Evidence 不可再生原则（证据层不删）。
长消息处理 = 证据保留 + 内容提炼，信息不丢。唯一风险（拆出低质 claim）用调研的质量监控兜底
（拆出条数分布 + 定向抽检）。

### 四.5 兜底设计（2026-08-19 用户拍板：双上限 + 默认隔离 + workbench 裁决）

**核心原则：超上限的 evidence 默认不进入系统计算（不自动拆条、不对账），留存 workbench 人工裁决。**

**两个上限：**

| 上限 | 内容 | 作用 |
|------|------|------|
| **evidence 字数上限** | 单条 evidence content 超过阈值（如 1500 字，待定）→ 不自动拆条 | 挡住"整篇文档样"的超大文本进入自动化管线 |
| **拆出条目上限** | 单次拆条调用拆出超过阈值（如 15 条）→ 不自动入库 | 挡住"为拆而拆"的密度异常内容 |

**超上限的处理流程（默认隔离，不丢弃）：**

1. **不自动拆条/不对账**——超上限 evidence 跳过自动化管线，`evidence_processing` 保持
   pending（或独立状态），内容**完整保留在 evidence 层**（Evidence 不可再生，不删）；
2. **留存 workbench 裁决**——这些 evidence 出现在 workbench 的"待裁决"视图（假说池/低置信视图），
   用户人工决定：手动拆分 / 手动概括 / 忽略 / 删除；
3. **用户裁决后才进入系统**——人工放行后走正常对账，或按用户意图处理。

**为什么这样设计（与"自动分诊"方案对比）：**

| | 自动分诊（先前方案） | **双上限 + 默认隔离（定案）** |
|---|---|---|
| 超限 evidence 去向 | 自动标记 + 自动分批拆条 | **不进自动化管线，留存人工裁决** |
| 风险 | 自动拆条拆坏大文本 → 污染比不处理更糟 | 无污染风险，质量由人工把关 |
| 成本 | 省人工（全自动） | 需人工裁决（个人场景可接受） |
| 适用 | 大规模、无人值守 | **个人记忆、用户信任优先**（本场景） |

**阈值待定**：evidence 字数上限（候选 1500 字）与拆出条目上限（候选 15 条）为工程初值，
可在 workbench 裁决数据积累后调整（哪些 evidence 频繁触发上限、裁决结果如何）。

**与其他定案的衔接：**
- 现实库 10+ 条"文档样"长消息（800–2383 字）部分会触发字数上限 → 默认不进自动化，留存 workbench 由用户裁决；
- 上限触发的 evidence 若用户判断"这其实是文档" → 与 §〇 定案 3（文档概括走 P2）衔接，等 P2 文档路径到位后走概括；
- MR-017 教训（不静默丢弃）依然成立：**超上限是"隔离 + 留给人看"，不是"丢掉"**。

### 四.6 结论

**无路径文档当长消息处理：可行且最优。** 它同时解决现实库那 10+ 条——全无路径，
全部按长消息拆条重建，不需要"舍弃"。且与 P2 文档概括（带路径走指针式）天然衔接。

## 七、对 M2.1 的影响（2026-08-19 定案后）

1. **claim-atomicity 规范**：增加"文档类证据例外"——**原子判据适用于对话类/长消息**；
   有路径文档（P2 采集时）走"概括 + 指针"分支，不进 M2.1 一期；
