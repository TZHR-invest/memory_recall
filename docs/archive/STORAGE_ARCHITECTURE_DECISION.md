# 记忆存储架构决策：单条 vs 多条

## 决策背景

用户提出核心问题：**是否应该把一个文本输入由大模型自动拆分为多条记忆存入数据库？**

---

## 方案对比

### 方案 A：单条记忆（当前实现）

```
输入：一篇 2000 字的日记
    ↓
存储：1 条记忆（包含完整内容）
    ↓
召回：返回整篇日记
```

**优点**：
- ✅ 实现简单，维护成本低
- ✅ 保持内容完整性，上下文不丢失
- ✅ 更新/删除操作简单（单条记录）
- ✅ 用户查看时看到完整内容

**缺点**：
- ❌ 向量被稀释（多主题混合）
- ❌ 召回精度低（可能返回不相关段落）
- ❌ Token 消耗高（每次召回整篇文档）
- ❌ 无法精准定位到具体时间段/事件

**适用场景**：
- 短文本（<300 字符）
- 单一主题
- 用户需要完整上下文

---

### 方案 B：多条记忆（分段存储）

```
输入：一篇 2000 字的日记
    ↓
LLM 分段：4 个时间段
    ↓
存储：4 条独立记忆 + 1 条索引记忆
    ↓
召回：返回相关段落
```

**优点**：
- ✅ 向量聚焦，召回精度高
- ✅ 按时间段/事件精准定位
- ✅ Token 消耗低（只返回相关段落）
- ✅ 支持复杂查询（"早上干嘛了"）

**缺点**：
- ❌ 实现复杂，需要关联管理
- ❌ 可能丢失上下文（分段边界）
- ❌ 更新/删除需要操作多条记录
- ❌ LLM 分段耗时（80-120s）

**适用场景**：
- 长文本（>300 字符）
- 多时间段/多主题
- 需要精准召回

## 混合方案（推荐）

**核心思路**：根据文本特征自动选择存储策略

```
输入文本
    ↓
判断特征（长度 + 主题数量）
    ↓
    ├─ 短文本 + 单主题 → 单条记忆
    └─ 长文本 OR 多主题 → 多条记忆
```

### 实现策略

| 文本特征 | 存储策略 | 说明 |
|---------|---------|------|
| **<300 字符** | 单条记忆 | 短文本，无需分段 |
| **300-1500 字符 + 单主题** | 单条记忆 | 中等文本，单一主题 |
| **300-1500 字符 + 多主题** | 多条记忆 | 中等文本，多主题需分段 |
| **>1500 字符** | 多条记忆 | 长文本，必须分段 |
| **>30K tokens** | Map-Reduce | 超长文本，分块处理 |

### 多主题检测

```python
# 方法 1：时间跨度检测
time_points = extract_time_points(text)
if len(time_points) > 3:
    return "多主题"

# 方法 2：段落主题检测
paragraphs = text.split('\n\n')
if len(paragraphs) > 3:
    return "多主题"

# 方法 3：LLM 判断（最准确）
prompt = f"这段文本包含几个不同的时间段或主题？返回数字。"
topic_count = llm.extract(prompt)
return topic_count > 1
```

## 当前实现问题

### 问题 1：分段阈值不合理

```python
# ❌ 当前实现：只有长度判断
if content_chars > threshold:
    return "分段"

# ✅ 改进方案：长度 + 主题数量判断
if content_chars > threshold or has_multiple_topics(content):
    return "分段"
```

### 问题 2：分段记忆没有关联

```sql
-- ❌ 当前实现：segment_ids 为空
SELECT id, input_type, segment_ids FROM memories WHERE id = 'xxx';
-- 结果：input_type = text, segment_ids = NULL

-- ✅ 改进方案：主记忆关联分段记忆
UPDATE memories 
SET segment_ids = ARRAY['seg1', 'seg2', 'seg3'],
    segment_count = 3
WHERE id = 'main_memory_id';
```

### 问题 3：召回时没有返回分段信息

```python
# ❌ 当前实现：只返回主记忆
def recall(query):
    return [memory1, memory2]  # 不包含分段记忆

# ✅ 改进方案：优先返回分段记忆
def recall(query):
    segments = search_segments(query)
    if segments:
        return segments
    return search_main_memories(query)
```

## 推荐方案

### Phase 1：修复当前实现（短期）

1. **降低分段阈值**：300 字符 → 200 字符
2. **添加多主题检测**：基于时间点数量判断
3. **修复分段关联**：主记忆的 `segment_ids` 字段正确填充
4. **召回优先级**：分段记忆 > 主记忆

### Phase 2：优化混合策略（中期）

1. **智能分段决策**：LLM 判断是否需要分段
2. **分段质量评估**：确保分段不会破坏上下文
3. **重叠窗口**：相邻分段有 10% 重叠，防止边界信息丢失
4. **分段摘要**：主记忆存储分段摘要，便于用户预览

### Phase 3：高级功能（长期）

1. **动态分段**：根据查询动态调整分段粒度
2. **层级存储**：日 → 周 → 月 → 年 聚合记忆
3. **跨文档关联**：不同文档之间的实体关系

---

## 决策结论

**推荐混合方案**：

| 文本特征 | 存储策略 | 召回策略 |
|---------|---------|---------|
| 短文本 + 单主题 | 单条记忆 | 直接召回 |
| 长文本 OR 多主题 | 多条记忆 | 召回分段记忆 |
| 超长文本 | Map-Reduce | 召回分块记忆 |

**核心原则**：
- ✅ 精准召回 > 完整性
- ✅ 效率 > 简单
- ✅ 自动化 > 人工配置

**实施优先级**：
1. 修复分段关联问题（P0）
2. 优化分段阈值和判断逻辑（P1）
3. 实现混合策略（P2）
